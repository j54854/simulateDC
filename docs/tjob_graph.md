# 搬送ジョブグラフ（TJob グラフ）の仕様

システム内の搬送ジョブ（`TJob`）をノードとし，ピッキング作業を行える順序をエッジで表す有向グラフの仕様．シミュレーション途中の状態の好ましさを評価し，ディスパッチングの意思決定（コントローラ）に用いることを目的とする．

> **ステータス**: オペレーショングラフ（[operation_graph.md](operation_graph.md)）の縮約としての定義を確定した（「オペレーショングラフからの導出（縮約）」の節．作業ブロックのポートと容量の項を含む）．現行実装（`gtp/graph.py`）は，1つの TJob を1ノードにまとめる旧版で，「ノード」「エッジ」「エッジの長さ」の各節はその仕様である．これらは縮約の定義に合わせて改訂する予定．エッジの長さは，運用ではまず，剛体近似の長さ（L0）を簡略化した L3 を使う（「エッジ長の簡略化（L3）」）．② 評価（最長経路長の計算）は未実装．現行実装の対象範囲は `gtps.unpicked_tjobs`．実装は「実装と運用の方針」の順（参照実装 → 直接構築 → 評価）で進める．

TJob の状態遷移とバケットの所在については [tjob_lifecycle.md](tjob_lifecycle.md) を参照．

---

## 設計方針

- **`models.py` とは切り離す**：グラフ関連は `gtp/graph.py` に実装し，`models.py` の状態を読み取るだけで書き換えない．`models.py` から `graph.py` は参照しない
- **コントローラから利用する**：`DefaultController` を継承したカスタムコントローラが `TJobGraph` を保持し，ディスパッチのたびに `update()` で最新のグラフを得る
- **構築と評価を分ける**
  - ① 構築（`TJobGraph.update()`）：物理的な状態と先行関係をそのまま表す．閉路を含んでよい．エッジには長さそのものではなく，長さの内訳を持たせる
  - ② 評価：パラメータ（α，β）から長さを計算し，閉路を除去する操作をはさんで最長経路長などを求める
- **段階的に実装する**：`update()` はまず毎回スクラッチから構築する素直な実装とし，実行時間を計測してから差分更新（ノード集合と先行関係エッジのみ保持し，経路順序エッジは張り直す）を検討する

```python
class MyController(DefaultController):
    def __init__(self, env, gtps):
        super().__init__(env, gtps)
        self.tjob_graph = TJobGraph(gtps)

    def dispatch_shuttle(self, shuttle, candidate_tjobs):
        g = self.tjob_graph.update()  # 現時点の状態を反映したグラフ
        ...
```

## オペレーショングラフからの導出（縮約）

TJob グラフを，オペレーショングラフのオンライングラフ（[operation_graph.md](operation_graph.md) の「オンライングラフ」）を縮約したものとして定義する．作業番号・記号は，この節の「記号」で定めるもの以外，すべて operation_graph.md に従う．

### 位置づけ

- 縮約は，オンライングラフのノード（作業）をいくつかずつ1つのノードにまとめ，エッジはまとめ方から機械的に導く操作である
- 縮約は**近似**である．ブロックの中の作業の間に no-wait 制約を課す「剛体近似」による（「長さ：剛体近似」を参照）．ただし作業ブロックだけは，コンベヤ（conv2）のところに継ぎ目を持ち，その上で待てる．評価に使うグラフの実体では，作業ブロックはこの継ぎ目で4つのノード（ポート）に分かれる（「作業ブロックのポート」）．下界の性質はオンライングラフの側に残し，縮約グラフはそれを近似するもの，という分担にする

### 記号

この節で使う記号をまとめて定める．詳しい説明は，右の列の節にある．

| 記号・用語 | 意味 | 詳しくは |
|---|---|---|
| G = (V, E, p, ℓ)，s | 時刻 t のオンライングラフ（作業の集合，エッジの集合，処理時間，エッジの長さ）と開始ノード | operation_graph.md |
| 鎖，区間 | 鎖は1つの TJob の作業の列．区間は鎖の連続した一部分 | operation_graph.md の「作業（ノード）」 |
| ブロック B | 縮約グラフのノード．1つの TJob の区間のうち，時刻 t で残っている作業の集合 | 「分割：3つのブロック」「時刻 t での分割」 |
| ブロックの型 | 到着・作業・帰還・再帰還の4つ | 同上 |
| φ(v) | 作業 v を，v が属するブロックに移す写像（φ(s) = s） | 「手続き」 |
| 資源 k | 2つの TJob の間の順序制約のもとになるもの．機械（シャトル・リフト・コンベヤの各セル・作業場），作業場順序，バケットの3種類 | 「オフセットの形」 |
| 確定・未確定 | 機械 m での訪問のうち，処理順が時刻 t で決まっているもの（m の鎖に入っているもの）が確定，決まっていないもの（鎖の末尾からの扇の先）が未確定 | operation_graph.md の「機械順序エッジ：鎖と扇」 |
| d(x, y) | 同じ鎖の上で，作業 x から作業 y の直前までの処理時間の和 | — |
| h(B) | ブロック B の先頭の作業（B の中で最初の未完了の作業） | 「時刻 t での分割」 |
| X(B) | ブロック B の時刻．h(B) の開始時刻．作業ブロックでは，代わりにポートごとの時刻を持つ（残っている最初のポートがブロックの時刻に当たる） | 「剛体近似」 |
| ポート Y・P・Q・O | 作業ブロックの中の4つの時刻．Y は荷卸し（15 の開始），P は搬入（17 の開始），Q は搬出の完了（19 の終了），O は積み出し（22 の終了）．ポートの間（conv2 の上と，ピッキング後の作業場の上）では待てる | 「作業ブロックのポート」 |
| e_B(k)，f_B(k) | ブロック B の資源 k に対する入口オフセット・出口オフセット（X(B) から測る．作業ブロックでは，その資源を使う部品のポートから測る） | 「オフセットの形」 |
| 項 | （ブロックの組，資源）ごとの f_B(k) − e_B′(k)．組のエッジの長さは，その資源についての max | 「オフセットの形」 |
| L0，L3 | L0 は剛体近似で定めた長さ（定義），L3 はそれをピッキング1回分を単位とする少数の整数に簡略化した，運用で使う長さ | 「エッジ長の簡略化（L3）」 |
| u，α | L3 の単位（ピッキング時間の代表値 ＋ 2t_C）と，設備の区間ごとの重み | 同上 |
| w | 割り付けていない台車の迎車を置き換える値（ループ1周）．クリティカルパスだけで評価するときに限って使う | 「作業ブロックのポート」 |

### 手続き

縮約は次の4つの手順からなる．

1. **分割**：V \ {s} をブロックに分ける．各ブロックは，1つの TJob の鎖の**連続した区間**とする．各作業 v を自分のブロックに移す写像を φ(v) と書き，φ(s) = s とする
2. **直列縮約（厳密）**：入ってくるエッジも出ていくエッジも鎖の工程エッジ1本だけの作業は，ノードを消し，前後の工程エッジを1本につなぐ（長さは和）．ループ搬送（13・23），挿入された周回（14・24），再搬送のループ搬送（34）がこれに当たる．この操作では最長経路が変わらない
3. **ブロック縮約**：縮約グラフのエッジを次のように定める
   ```
   E' = { (φ(u), φ(v)) : (u, v) ∈ E,  φ(u) ≠ φ(v) }
   ```
   同じブロックの中のエッジは消える．1組のブロックの間に元のエッジが複数あるときは，それぞれを換算した長さの最大値がその組の長さになる．ただし，グラフには（組，資源）ごとの項として持ち，max は評価のときにとる（「実装と運用の方針」を参照）
4. **冗長エッジの除去（任意）**：最長経路を変えないエッジ（推移的に導かれるものなど）を除く

どのブロックの組にエッジを張るかは手順3で自動的に決まる．設計上の選択になるのは，分割（手順1．「分割：3つのブロック」「時刻 t での分割」）と，長さの換算規則（「長さ：剛体近似」）だけである．

### 分割：3つのブロック

TJob の鎖全体をどこで切るかを定める．TJob ごとに，鎖をループで2か所切り，3つのブロックに分ける．

```
到着ブロック 1–12 | 13（直列縮約）| 作業ブロック 15–22 | 23（直列縮約）| 帰還ブロック 25–33
```

| ブロック | 作業 | 使う機械 |
|---|---|---|
| 到着 | 1〜12 | S(a, f)，conv0^FW(a, f)，E^FW(a)，conv1^FW(a)（11・12 は台車も） |
| 作業 | 15〜22 | conv2^FW(p)，W(p)，conv2^BW(p)（15・21・22 は台車も） |
| 帰還 | 25〜33 | conv1^BW(a)，E^BW(a)，conv0^BW(a, f)，S(a, f)（25 は台車も） |

再搬送のときに現れる4つめの型（再帰還）は，「時刻 t での分割」の (b) で定める．定義は復路まで含めて与え，実装も往路と復路を同時に扱う（対象範囲は `unrestored_tjobs`．「実装と運用の方針」を参照）．

**ループで切る理由**：

- オンライングラフでは台車が扇を持たないので，ループの区間（13・23）をまたいで，異なる TJob の作業を結ぶエッジはない．作業 13・23 は直列縮約でき，ここで切っても区間の間に余計なエッジは生じない
- 周回・再搬送の挿入（U3）が起きるのはちょうど 13 → 15 の間なので，その代償を区間の間のエッジで扱える（「周回・再搬送の代償（評価の規則）」）

区間をまたいで異なる TJob を結ぶのは，シャトルの鎖と扇（帰還 ↔ 到着．入庫と出庫が同じシャトルを使うため）と，バケットエッジ（帰還 → 到着）だけである．

### 長さ：剛体近似

縮約グラフのエッジの長さを，元のエッジからどう換算するかを定める．

#### なぜ近似が要るか

**代表作業による厳密な縮約**：ブロック B の時刻を，B の中の代表作業 r(B) の開始時刻とする．B に入ってくるエッジがすべて r(B) 以前の作業に入り，出ていくエッジがすべて r(B) 以後の作業から出るなら，元のエッジ u → v を次の長さに換算すれば，最長経路が保たれる．

```
ℓ'(B, B') = d(r(B), u) + ℓ(u, v) + d(v, r(B'))
```

**3区間ではこの条件が成り立たない**．外から入るエッジと外へ出るエッジがかかる作業が，区間の中で入り混じっているからである（開始エッジを除く）．

| ブロック | 外から入るエッジがかかる作業 | 外へ出るエッジがかかる作業 |
|---|---|---|
| 到着（1〜12） | 1, 4, 5, 6, 9, 10 | 4, 5, 7, 9, 10, 12 |
| 作業（15〜22） | 15, 16, 17, 19, 20 | 15, 16, 17, 19, 20, 22 |
| 帰還（25〜33） | 25, 26, 27, 29, 30, 31 | 26, 27, 29, 30, 31, 33 |

1つのブロックが複数の機械をまたぎ，各機械でのブロッキングがそれぞれ別の作業にかかるためである．この粒度で縮約する限り，縮約は近似になることが避けられない．

#### 剛体近似

ブロックの中では待たないと仮定し，ブロックを1つの塊として扱う（ブロックの中で隣り合う作業の間に no-wait 制約を課すことに当たる．ブロックの間では元のとおり待ってよいので，待ちはすべてブロックに入る前に寄せられる）．

- ブロック B の時刻 X(B) は，先頭の作業 h(B) の開始時刻とする．B の作業 v の開始時刻は X(B) + d(h(B), v) に固定される
- 元のエッジ u → v（u ∈ B，v ∈ B′）を，次の長さに換算する
  ```
  ℓ'(B, B') = max over (u, v) of [ d(h(B), u) + ℓ(u, v) − d(h(B'), v) ]
  ```
- ブロッキングの情報をすべて残せる．ただし，元のグラフより制約を強める（ブロックの中で待つことを許さない）ので，**下界の性質は失われる**．実際にはコンベヤの上で待てるところを，剛体近似ではブロックの開始を遅らせることで帳尻を合わせるので，混雑時には遅めの見積りになる
- 作業ブロックだけは，コンベヤ（conv2^FW・conv2^BW）のところに継ぎ目を設け，その上で待つことを許す．この遅めの見積りが作業場の稼働率の指標を直接ゆがめるためである（「作業ブロックのポート」）

**なぜ「強める」のか**：d(h(B), v) は，h(B) から v までの間隔の下界である．そのため，この値に固定すると一見楽観的に見えるが，次のとおり，実際には制約が加わる．

| | h(B) と v の開始時刻 S の関係 | 意味 |
|---|---|---|
| 元のグラフ（工程エッジ） | S(v) − S(h) ≥ d(h, v) | 間隔は d 以上．途中でいくら待ってもよい |
| 剛体近似 | S(v) − S(h) = d(h, v) | 上の式に加えて，S(v) − S(h) ≤ d(h, v)（待ちの上限 0）が加わる |

- 加わるのは S(h) ≥ S(v) − d(h, v)，つまり「**v が遅れるなら，h もその分だけ遅れなければならない**」という後ろ向きの制約である．元のグラフにはこの向きの制約がない
- 前向き（h から v）には，剛体近似でも v は X(B) ＋ d より早くならないので，元のグラフより早まることはない
- したがって，剛体近似で許されるスケジュールは，元のグラフで許されるスケジュールの一部である．最早開始時刻は元のグラフ以上になり，オンライングラフが持っていた下界の性質は保証されなくなる
- 例：リフトを待つ j（後述の「例：同じ階の置場で出庫を待つ i, j（シャトルの順は i → j）」で，リフトの行が max になる場合）は，元のグラフではシャトルで早く出て conv0 の上で待てる．剛体近似ではそれが許されないので，リフトが空く時刻から逆算して j の迎車（h）が遅らされ，シャトルの解放も遅れる．その遅れは，同じシャトルを次に使う TJob に伝わる

#### オフセットの形

剛体近似の長さを，資源ごとの項に分けて書き直す．元のエッジはどれも，「ある資源 k を，i が使い終えてから j が使い始める」という形をしている．そこで，ブロック B と資源 k について，2つのオフセットを定める．

| 記号 | 意味 | 定義 |
|---|---|---|
| e_B(k) | 入口オフセット：B が k を使い始める時刻（X(B) から測る） | d(h(B), k を使う最初の作業) |
| f_B(k) | 出口オフセット：B が k を手放す時刻（X(B) から測る） | d(h(B), k を使う最後の作業) ＋ その処理時間 ＋ 復帰時間 r_k |

剛体近似の長さは，次のように書ける．

```
ℓ'(B, B') = max over 資源 k of [ f_B(k) − e_B'(k) ]
```

max は，B が B′ より先に k を使うことがオンライングラフで確定している（鎖または扇のエッジがある）資源 k についてとる．意味は「B′ が k を使い始めるまでに，B が k を手放していなければならない」である．

資源ごとの f_B(k) − e_B′(k) を，（組，資源）ごとの**項**と呼ぶ．組の長さは項の max で，グラフには項のまま持ち，max は評価のときにとる（「実装と運用の方針」）．

作業ブロックでは，オフセットを，その資源を使う部品のポートから測る．作業場は P から使い始めて Q で手放し，作業場順序は Y で表す．conv2 のセルの項は，容量・順序の項に置き換える（「作業ブロックのポート」）．

**「剛体近似」の式との関係**：2つの式は同じものである．元のエッジ u → v（u ∈ B，v ∈ B′）は，どれもちょうど1つの資源 k から来ている．

| 資源 k | u | v | ℓ(u, v) |
|---|---|---|---|
| 機械（セルを含む） | B が k を使う最後の作業 | B′ が k を使う最初の作業 | p(u) ＋ r_k（機械順序エッジ） |
| 作業場順序 | B の 15 | B′ の 15 | p(15) = t_L^L |
| バケット | B の 33 | B′ の 1 | p(33) ＋ (Z − z)·t_S^M |

これを「剛体近似」の式の各項に入れると，次のように分かれる．

```
d(h(B), u) + ℓ(u, v)  =  d(h(B), u) + p(u) + r_k  =  f_B(k)    （B が k を手放す時刻）
d(h(B'), v)                                         =  e_B'(k)   （B′ が k を使い始める時刻）
```

- 1組のブロック (B, B′) の間で，1つの資源 k から出るエッジは高々1本である．ブロックの中で同じ機械を2回訪れることはない（再搬送の2回目の訪問は別のブロックになる）．したがって，max over (u, v) と max over k は範囲が1対1に対応する
- f_B(k) に復帰時間 r_k が入るのは，機械順序エッジの長さに復帰時間が含まれるためである
- セルの場合，「k を使う最後の作業」はそのセルから出す作業，「最初の作業」はそのセルに入れる作業である．これがブロッキングを表す
- 同じ TJob のブロックの間のエッジ（到着 → 作業など）は資源から来るものではないので，max over k には含めず，「同じ TJob のブロックの間のエッジと開始エッジ」で別に扱う

#### 例：同じ階の置場で出庫を待つ i, j（シャトルの順は i → j）

A_x = p(1) ＋ p(2) ＋ p(3) = 2(Z − z_x)·t_S^M ＋ t_S^L とする（x の迎車・荷積み・搬送）．i, j は同じ階 f にあるので，同じシャトル・conv0・リフトを使う．

| 資源 | f_i − e_j |
|---|---|
| シャトル S(a, f) | (A_i ＋ t_S^L) − 0 |
| conv0^FW[0] | (A_i ＋ t_S^L ＋ t_C) − A_j |
| conv0^FW[c]（1 ≤ c < C₀ − 1） | A_i − A_j ＋ 2t_C |
| conv0^FW[C₀ − 1] | A_i − A_j ＋ t_C ＋ f·t_E^M ＋ t_E^L |
| 往路リフト E^FW(a) | A_i − A_j ＋ 2f·t_E^M ＋ 2t_E^L |

デフォルトのパラメータ（t_S^M = t_E^M = 0.2，t_S^L = t_E^L = 5，t_C = 1）では，max はシャトルかリフトの行になる．リフトの行からシャトルの行を引くと 0.2·2(f − (Z − z_j)) なので，j の置場が待機ノードに近い（Z − z_j < f）ときはリフトの行が max になる．これは，剛体近似では j が conv0 の上で待てないため，「j がリフトに着いたときにリフトが空いている」ように j の迎車の開始を遅らせることを表している．i と j が別の階にある場合は，共有する資源はリフトと conv1 だけになり，長さはリフトの行（e_j は j の階で計算する）になる．

#### 負の長さ

f_B(k) − e_B′(k) は負になりうる．B′ が資源 k に着くまでの道のり e_B′(k) が長く，B を待たなくてよい場合である．負になりうるのは，主に異なる TJob のブロックの間のエッジである．

- 例：同じ階で i, j の順に出庫する場合，conv0^FW[0] の項は (A_i ＋ t_S^L ＋ t_C) − A_j になる（A_x は x の迎車・荷積み・搬送の時間．前述の「例：同じ階の置場で出庫を待つ i, j（シャトルの順は i → j）」の表）．i が待機ノードのすぐ隣の段（z_i = Z − 1），j が最も遠い段（z_j = 0）にあると，デフォルトのパラメータ（Z = 45）では A_i = 5.4，A_j = 23 なので，この項は 5.4 ＋ 5 ＋ 1 − 23 = −11.6 になる．j がシャトルで運ばれてくるより前に，i はとうに conv0 の先頭セルを出ているので，このセルは j を待たせない（この組の長さ自体は，シャトルの項が max になるので正である）
- 例（max そのものが負になる場合）：i が conv1^FW(a) の末尾で台車を待ち，j が同じ系列の置場で出庫を待っている（階は問わない）．i はシャトルとリフトをもう終えているので，j と共有しうる資源は conv1 のセルだけで，j には末尾セルの鎖の末尾 i から扇のエッジが入る．f_i ＝ p(11) ＋ p(12) ＝ 0 ＋ 1 ＝ 1（未割付けの台車の迎車の名目値は 0）である．e_j は，j がシャトル・conv0・リフト・conv1 を経て末尾セルに入るまでの時間で，荷卸し・移載を合わせると20秒を超える．e_j = 21 とすると，ℓ′(i, j) = 1 − 21 = −20 になる
  ```
  時刻 →
  i : X(i) ─[11, 12: 1秒]→ 末尾セルを出る
  j : X(j) ─[シャトル・conv0・リフト・conv1: 21秒]→ 末尾セルに入る

  資源の上での制約 : X(j) + 21 ≥ X(i) + 1
  先頭どうしで表すと: X(j) ≥ X(i) − 20
  ```
  i と j が同じ時刻に出発すると，末尾セルは i が出てから j が入るまで20秒空く．負の長さは，この隙間の分だけ j が i より先に出発してよいという**余裕**を表す（20秒空けなければならないという意味ではない）．正の長さが「少なくともこれだけ後に」を表すのに対し，負の長さは「これだけ先までなら許される」を表す．マイナスが出るのは，資源に着く時点での比較を，ブロックの先頭の時刻に引き戻して表しているためである．このエッジはふつう効かないが，X(i) が大きく遅れれば効きうるので，定義としては残す（除くかどうかは未決事項5）
- 同じ TJob のブロックの間のエッジは処理時間の和なので，負にならない．開始エッジ s → B も長さ 0 である
- バケットエッジから来る項も負にならない．終点が到着ブロックの先頭の作業 1 なので，e = 0 だからである
- オンライングラフの開始エッジ（復帰中の機械からのもの）を換算した項 r − d(h(B), v) は負になりうる．ただし，長さ 0 の s → B と並ぶので，負の値は効かない

最長経路の計算には差し支えない（閉路がないので，正の閉路の心配もない．「閉路がないこと」）．なお，「実装と運用の方針」の方式2（オフセットを固定の原点から測る）では，s → B の長さ −d(原点, 今の先頭) が意図して負になる．これは表し方の都合で，最長経路の値は変わらない．

#### エッジの種類

エッジの種類は，どの資源から来たかで決まる．

| 資源 k | オンライングラフのエッジ | 縮約グラフの種類 |
|---|---|---|
| シャトル（出庫どうし），往路リフト，conv0^FW・conv1^FW の各セル | 機械順序エッジ | `aisle` |
| 作業場 W(p)，conv2^FW・conv2^BW（セルの代わりに容量・順序の項．「作業ブロックのポート」） | 機械順序エッジ | `station` |
| 作業場順序（作業 15 を擬似的な資源とみなす．作業ブロックのポート Y で表し，Y_k ≥ Y_i ＋ t_L^L） | 作業場順序エッジ | `precedence` |
| バケット（i の作業 33 を手放し，j の作業 1 で使い始める．f に復帰時間 (Z − z)·t_S^M を含む） | バケットエッジ | `bucket` |
| 復路の機械（conv1^BW・復路リフト・conv0^BW・シャトルの入庫を含む組） | 機械順序エッジ | `aisle` と同様の系列側の種類とする．名前は未決事項9とあわせて決める |

#### 同じ TJob のブロックの間のエッジと開始エッジ

同じ TJob のブロックの間には，直列縮約した工程エッジから次のエッジができる．

| エッジ | 長さ |
|---|---|
| 到着 → 作業 | d(h, 12) ＋ p(12) ＋ p(13)（到着区間を終えてループを渡る時間）．作業ブロックのポート Y に入る |
| 作業 → 帰還 | 作業ブロックのポート O（作業 22 の終了）から p(23) |

- **開始エッジ**：すべてのブロックに s → B（長さ 0）を張る．どのブロックも時刻 t より前には始まらないので，剛体近似のもとでも正しい制約である．オンライングラフの開始エッジ（復帰中の機械からのものを含む）も，剛体近似の規則で換算する

#### 作業ブロックのポート

剛体近似のままでは，コンベヤがバッファとして働かない．例：conv2^BW の末尾のセルで l が台車を待つと，後ろでピッキング中の k は，セルの項によってブロック全体がずらされ，作業場で搬出を待つことになる．実際には k はピッキングを終えて手前のセルまで進んで待つので，作業場は空く．剛体近似では台車を待つ TJob が1台いるだけで作業場が塞がったように見え，稼働率の指標がゆがむ．conv2^FW が満杯のとき，台車は接続口で空きを待つ（後続の台車を止め，押し出しによる周回を招きうる）．この空き時刻も，作業場の項から逆算した遅すぎる値になり，正しく表せない．

作業レベルのオンライングラフでは，作業の間で待てるので，コンベヤの容量は正しく表されている．そこで，作業ブロックの中に4つの時刻（**ポート**）を持たせ，コンベヤのところだけ待つことを許す．

**グラフの実体**：鎖の切り方（3区間というブロックの粒度）は変えない．ただし，作業ブロックはポートで4つのノード Y・P・Q・O に分かれ，評価（最長経路・直列化）に使うグラフの実体は，この分割後のグラフである（1つの TJob は，到着1・作業4・帰還1の6ノードになる）．ブロック単位のグラフは，それを束ねて見たものとして扱う．

- ブロック単位で見ても変わらないもの：エッジの種類（`station`・`precedence`・`aisle`・`bucket`），TJob の位置の分類と状態ごとのブロックの構成（「時刻 t での分割」）．GNN や特徴量の入力では，ブロックをノードとし，ポートの時刻をノードの属性，項の端点のポートをエッジの属性として持たせれば，この粒度を保てる
- 分割後のグラフで見ると自然になるもの：過ぎたポートを取り除く規則（「時刻 t での分割」の一般規則）は，完了したノードを消すふつうの規則になる．閉路がないことの補題4も，ブロックの中の Y → P → Q → O を含めた，分割後のグラフについての主張である（「閉路がないこと」）

```
  Y ──(conv2^FW)──> P ──(作業場)──> Q ──(conv2^BW)──> O
  荷卸し（15 の開始） 搬入（17 の開始） 搬出の完了（19 の終了） 積み出し（22 の終了）

  P ≥ Y ＋ d_FW               d_FW ＝ t_L^L ＋ (C₂ − 1)·t_C（conv2^FW の上で待ってよい）
  Q ≥ P ＋ t_C ＋ t_P ＋ t_C   （作業場の上で，ピッキング後に搬出を待ってよい）
  O ≥ Q ＋ d_BW ＋ 迎車        d_BW ＝ (C₂ − 1)·t_C ＋ t_L^L（conv2^BW の上で待ってよい）
```

ポートとポートの間の作業の列は剛体のままである．ブロックは，剛体の部品をコンベヤのところで伸び縮みできる継ぎ目でつないだものになる．

**項が単純になること**：負の長さは，資源を使う時刻をブロックの先頭まで引き戻して比べることから生じる（「負の長さ」）．ポートを入れると，オフセットを測る起点が資源を使う作業のすぐそばに来るので，引き戻しがほとんどなくなる．その結果，作業ブロックに出入りする項（下の表）とブロックの中の項は，どれも組によらない 0 以上の定数になる．ポートなしの剛体近似では，同じ組に conv2^FW の各セル・作業場・conv2^BW の各セルの項（約 2C₂ ＋ 1 本）が並び，それぞれの値を d(h, ·) の差として組ごとに計算する必要があった（conv2^BW のセルの項は，e にピッキング時間までが入るので大きく負になりやすく，大半は max で負けるか負になる）．ポートは，作業ごとの時刻を持つオンライングラフ（エッジはすべて 0 以上）と，時刻を1つにまとめる剛体近似（負の長さと組ごとの値が出る）の中間で，待てる場所（バッファ）で時刻を分けるので，分けた先の項は作業レベルと同じ単純な形に戻る．したがって，ポートを入れても，項の数・値の計算・負の長さのどの点でも複雑にはならず，むしろ単純になる．増えるのはノードの数（評価で扱う時刻の数）だけである

**作業ブロックに出入りする項**（i は作業場の順で k より前の TJob．C₂ はコンベヤのセル数）

| 項 | 種類 | 不等式 |
|---|---|---|
| 到着 → 作業 | 同じ TJob | Y_k ≥ 到着ブロックの時刻 ＋ 長さ（評価では周回の規則を当てる） |
| 作業場順序 | `precedence` | Y_k ≥ Y_i ＋ t_L^L |
| 往路の容量 | `station` | Y_k ≥ P_{k−C₂} ＋ t_C（conv2^FW に空きがある） |
| 作業場 | `station` | P_k ≥ Q_i（i は作業場の順で直前．扇の先は鎖の末尾から） |
| 復路の容量 | `station` | Q_k ≥ O_{k−C₂}（conv2^BW に空きがある） |
| 復路の順序 | `station` | O_k ≥ O_{k−1} ＋ t_L^L（前の TJob が台車に載ってから） |
| 作業 → 帰還 | 同じ TJob | 帰還ブロックの時刻 ≥ O_k ＋ ループ搬送 |

- conv2^FW・conv2^BW のセルの項は，容量と順序の項に置き換える．セルの間の移動時間の端数は省き，コンベヤを容量 C₂ の FIFO のバッファとみなす．容量と順序の項は，オンライングラフのセルの鎖から導かれる制約である
- 「k − C₂」「k − 1」は作業場の順（conv2 の FIFO の順）で数える．順序が未確定の TJob（まだ荷卸しされていない TJob）には，確定した列の末尾から数えて C₂ − 1 台前の TJob から，未確定のすべての作業ブロックへ容量の項を張る（扇と同じ考え方）
- 他の TJob の到着・帰還ブロックとの項（シャトル・リフトなど）は，作業ブロックにはかからない．作業ブロックが使う資源は，作業場・conv2・作業場順序だけだからである
- **迎車**：グラフの名目値は，オンライングラフと同じく，台車を割り付けていなければ 0，割り付けた後は台車の位置からの値 d_L(台車の位置, 接続口)·t_L^M とする．台車を待つ時間は，評価の直列化で台車を資源として扱うことで入れる（「実装と運用の方針」の評価）．その待ちが復路の容量の項を通じて作業場の閉塞として現れる仕組みは，このポートと容量の項による
  - クリティカルパスだけで評価する場合（直列化をしない場合）に限り，割り付けていない台車の迎車を w ＝ L（ループ1周 N_L·t_L^M）に置き換えるパラメータを持つ．割り付けた後の迎車は1周を超えないので，台車を差し立てると見積りが必ず縮み，長くなることがない．1/2周のような中間の値は，下界の考え方（0）とも，差し立てで縮む性質（1周）とも合わないので使わない
- 時刻 t で，すでに過ぎたポートは取り除く（「時刻 t での分割」の一般規則）
- 到着・帰還ブロックの conv0・conv1 も，剛体近似ではバッファとして働いていない（例：リフトを待つ j のシャトルでの出庫が遅らされる）．同じ扱いを広げられ，項が単純になる利点も同じく得られる．ただし，広げるほどノードが増えてオンライングラフに近づく．稼働率に直接効くのは作業ブロックなので，まず作業ブロックだけに入れ，他はポートの有無による比較（未決事項13）で要否を決める
- 剛体近似のずれは，下流（台車への到達 O）にはほとんど出ない．先頭の TJob が台車に載るとき，後ろの TJob も順に1セルずつ前進できるので，剛体近似でも O はセル間の移動時間の端数しか変わらない．ずれは上流に波及する．conv2^BW 側では作業場の解放 Q と次のピッキングの開始 P に，conv2^FW 側では荷卸し Y（周回の判定）に出る．台車待ちは最大でループ約1周（L3 で 2）なので，1回の台車待ちで作業場の稼働の見積りがピッキング1〜2回分ずれうる．これが作業ブロックにポートを入れる理由である

### 時刻 t での分割

「分割：3つのブロック」は TJob の鎖全体についての切り方である．ここでは，時刻 t のオンライングラフ（未完了の作業だけからなる）で，実際にどのブロックができるかを定める．

#### 一般規則

- **ブロックは残っている作業からなる**：区間のうち未完了の作業だけでブロックを作る．すでに終えた区間のブロックは持たない
- **先頭の作業 h(B)**：区間の中で最初の未完了の作業．実行中なら，その処理時間は残り時間（名目値の規則どおり）とする
- **すでに使っている資源**：B が今まさに占有している資源 k（例：conv0 のセル c にいるバケットにとってのセル c）は，入口の作業が完了しているので e_B(k) を定義しない．k について B は鎖の先頭側にいるので，B へ入るエッジはなく，出口オフセット f_B(k) だけが要る
- **開始エッジ**：s → B は長さ 0（実行中の作業も，オンライングラフでは s から長さ 0 で始まる）
- **作業ブロックのポート**：すでに過ぎたポートは，完了した作業と同じく取り除き，残っているポートだけを持つ．過ぎたポートに出入りしていた項も消える

#### 状態ごとのブロックの構成

一般規則だけで，次の場合は特別な扱いなしに決まる．

| TJob の状態（現行実装の位置） | ブロック |
|---|---|
| 置場で出庫待ち・迎車中（`store`） | 到着（1〜）・作業・帰還 |
| conv0・リフト・conv1 の上（`conv0`・`lift`・`conv1`，移動中または待ち） | 到着（残り）・作業・帰還 |
| conv1 の末尾で台車を待つ（11 が未着手．未割付けなら迎車の名目値は 0） | 到着（11〜12）・作業・帰還 |
| 順番待ち（`off_route`） | 到着（1〜）・作業・帰還．到着ブロックには `bucket` が入る |
| conv2 の上（`conv2`） | 作業（残り．conv2^FW の上なら P・Q・O，conv2^BW の上なら O のポートが残る）・帰還 |
| 作業場でピッキング中（`station`） | 作業（18 の残り〜22．Q・O のポートが残る）・帰還 |

#### 個別に定める場合

**(a) ループ上の TJob**（`car`．作業 13，または挿入済みの周回 14 が実行中か，接続口で待っている）

- 到着ブロックはない．実行中の 13 は，入るエッジが s からのものだけ，出るエッジが 15 への工程エッジだけなので，直列縮約できる
- 結果は s → 作業ブロック（長さ ＝ ループの残り時間の名目値．ポート Y に入る）．接続口で待っている場合は 13 が完了しているので長さ 0
- 復路（23）も同じ

**(b) 再搬送中の TJob**（`beyond_store`）．再搬送が決まると（U3），鎖は次のようになる．

```
34 | 25–33 | 1–12 | 13 | 15–22 | 23 | 25–33
   | 再帰還 | 到着 |    | 作業  |    | 帰還
```

- 34（再搬送のループ搬送 P_p^FW → A_a^BW）は，23 と同じく直列縮約する
- 25〜33 は，帰還ブロックと同じ機械を同じ順に使うので，帰還型のブロック（**再帰還ブロック**）とする
- 再帰還 → 到着のエッジは，同じシャトルの2つの訪問の間の機械順序エッジから，長さ d(h, 33) ＋ p(33) ＋ (Z − z)·t_S^M になる
- オンライングラフは今後の再搬送を予測しないので，再帰還ブロックが現れるのは再搬送が決まった後だけである

**(c) 空になるバケット**：作業ブロックは 15〜18 で終わり（19〜22 はない），帰還ブロックはない．W(p) の最後の作業は 18 なので，作業場を手放すのは 18 の終了である．ポートは Y・P と，Q の代わりに 18 の終了（Q ≥ P ＋ t_C ＋ t_P）だけを持ち，O と復路の容量・順序の項はない．作業場の項は，この時刻から出る．後続の `bucket` もない

#### 先頭が実行中のブロック

剛体近似では，入るエッジによって X(B) > 0 になりうる．先頭の作業 h(B) が使っている資源には入るエッジがない（一般規則）ので，X(B) を決めるのは h(B) より後の作業 v へ入るエッジ，つまり v が別のエッジで待たされる場合である．

このとき剛体近似はブロック全体を X(B) だけ後ろへずらすので，すでに始まっている h(B) の開始時刻も後ろへずれる．これは文字どおりには起こりえないが，h(B) の開始時刻から出るエッジはないので，「h(B) は予定どおり終わり，その機械を占有したまま X(B) だけ待つ」と読み替えられる．no-buffer なのでこれは実現可能な動きであり，他の TJob に伝わる制約は正しい．

誤差は，実際には v の直前まで進んでから待てることから生じる．h(B) の機械を含め，v の直前の作業より前に手放す資源は，実際には剛体近似より最大 X(B) 早く解放される．剛体近似はこの解放を遅く見積もるので，誤差は悲観側に出る．これは未着手のブロックでも同じく生じる剛体近似の一般の誤差で，先頭が実行中であることに固有の誤差はない．作業ブロックでは，搬出の待ちはポート P と Q の間の継ぎ目で表され，ピッキング後に作業場の上で待てるので，ピッキング中の場合に誤差はない．誤差の大きさは未決事項8で確かめる．

### 閉路がないこと

縮約グラフは閉路を持たない．エッジの長さによらない構造の性質なので，剛体近似で負の長さが出ても，正の閉路の心配はない．

**なぜ自明ではないか**：閉路を持たないグラフでも，ノードをまとめると閉路ができることがある．ブロック A の作業 a1 → ブロック B の作業 b1（資源 k1 で A が先）と，B の作業 b2 → A の作業 a2（資源 k2 で B が先）があると，作業のレベルでは a1 → b1 → b2 → a2 と一方向に流れていても，縮約すると A → B → A になる．ブロックは時間的に長いので，2つのブロックが重なっていると，資源ごとに「A が先」と「B が先」が両方成り立ちうる．

3区間のブロックでも，事後グラフ（実際の処理順がすべて決まったグラフ）を鎖全体のまま縮約すると，閉路ができる．到着ブロックと帰還ブロックが共有する機械はシャトルだけ（リフトと conv0 は出庫用・入庫用で別）なので，閉路は「シャトルで到着から帰還へ → 入庫リフトで帰還どうし → 別の階のシャトルで帰還から到着へ → 出庫リフトで到着どうし」という回り道になり，4つの TJob が要る．系列 a で，時間の順に次のことが起きる場合である．

1. シャトル f が j を出庫する．j は conv0^FW(f) に出て，出庫リフトを待ち始める
2. 入庫リフトが i を運び，その後で l を運ぶ（帰還_i → 帰還_l，E^BW）
3. i が階 f に戻り，シャトル f が i を入庫する．j の出庫の後なので，到着_j → 帰還_i（S(a,f)）
4. l が階 f′ に戻り，シャトル f′ が l を入庫し，その後で q を出庫する（帰還_l → 到着_q，S(a,f′)）
5. 出庫リフトが，待っている j より先に q を運ぶ（到着_q → 到着_j，E^FW）

```
到着_j →(S(a,f): j の出庫が先) 帰還_i →(E^BW: i が先) 帰還_l →(S(a,f'): l の入庫が先) 到着_q →(E^FW: q が先) 到着_j
```

j の到着ブロックは 1 から 5 の後まで続くので，その間の出来事と両側でつながる．これは正の閉路で，剛体近似（j は conv0 で待たない）と実際（j は待つ）が矛盾する．

**オンライングラフでは起きない理由**：時刻 t のオンライングラフで，この4本が同時に張られることはない．

- 到着_q → 到着_j（出庫リフトで q が先）は，オンライングラフが確定した順序しか持たず，扇も鎖の末尾からしか出ないので，q がリフトの鎖に入っているか鎖の末尾であるときにだけ張られる．そのとき q は出庫を終えて conv0 にいる
- 帰還_l → 到着_q（シャトル f′ で l の入庫が先）は q のシャトルの作業に入るエッジだが，上のとき q はシャトルの作業を終えているので，完了した作業とともに消えている（U4）

どの時刻で切っても，閉路のうち少なくとも1本は，過去の作業か，まだ決まっていない順序に掛かるので，オンライングラフにはない．以下の補題1〜4は，これがどの場合にも成り立つことを示す．

**補題1（エッジが出る条件）**：ブロック B から別の TJob のブロックへ機械順序エッジが出るのは，B のその機械での訪問が確定している（鎖に入っている．「記号」を参照）ときだけである．未確定の訪問には扇のエッジが入るだけで，そこからは出ない．作業ブロックの容量・順序の項も，conv2 のセルの鎖から導かれるものなので，機械順序エッジとして扱う（出るのは確定した列の TJob からだけである）．

これに基づいて，ブロックを2つに分ける．

- **C ブロック**：機械順序エッジを1本以上出すもの（どこかの機械で確定している）
- **N ブロック**：機械順序エッジを出さないもの．出るのは `precedence`・`bucket`・同じ TJob の次のブロックへのエッジだけ

**補題2（N ブロックからは N ブロックにしか行けない）**：N ブロックから出るエッジの行先はどれも N ブロックで，キー（`pjob.idx`, `tjob.idx`, 区間の順：再帰還 < 到着 < 作業 < 帰還）が真に増える．

- `precedence`：行先は後の PJob の作業ブロック．先の PJob の TJob が荷卸し前なので，後の PJob の TJob も荷卸しされておらず（`TJob.late_preceding_tjob_count()`），conv2^FW 以降のどの機械でも未確定
- `bucket`：行先は順番待ちの TJob の到着ブロックで，どの機械でも未確定．キーが増えることは「閉路の性質」の根拠と同じ
- 同じ TJob の次のブロック：到着が残っていれば作業ブロックは未確定（conv2^FW[0] に荷卸しされていない），作業が残っていれば帰還ブロックは未確定，再帰還の後の到着ブロックは未確定．このエッジは C ブロックから出ても，行先は必ず N ブロックになる

**補題3（C ブロックの間のエッジの型）**：C ブロックどうしを結ぶのは，同じ型の間の機械順序エッジと，シャトルの扇の「到着（末尾）→ 帰還」だけである．逆向きの「帰還（末尾）→ 到着」の行先は置場で出庫を待つ TJob で，どの機械でも未確定なので N ブロックになる．したがって C ブロックの間では，型は「到着 → 帰還」の一方向にしか移らず，作業型は他の型とつながらない．

**補題4（同じ型の中に閉路はない）**：系列 a の到着型の C ブロックは，「conv1^FW(a) に入る実際の（将来の）順」で一列に並び，すべてのエッジがこの順と同じ向きになる．シャトル・conv0・リフト・conv1 は，この順を FIFO で引き継ぐからである．実際のスケジュールはオンライングラフのすべての制約を満たすので，この並べ方は必ず存在する．同様に，作業型は「conv2^FW(p)[0] に荷卸しする実際の順」（`precedence` もシミュレータが守る），帰還型は「conv1^BW(a)[0] に荷卸しする実際の順」で一列に並ぶ．作業ブロックのポートの間の項（容量・順序）も，同じ作業場の中で作業場の順に前から後ろへ向かうので，この並べ方と同じ向きであり，ブロックの中も Y → P → Q → O の一方向である．

**結論**：閉路は N ブロックを通れず（補題2），C ブロックだけの閉路は型をまたげず（補題3），同じ型の中にもない（補題4）．

- 前提：「閉路の性質」と同じく，PJob を `pjob.idx` の順に投入すること（補題2のキーの増加）
- 確認：実装したら，各時点の縮約グラフが DAG であることを `assert` とテストで確かめる（現行の閉路の観察と同じ3条件で）

### 周回・再搬送の代償（評価の規則）

作業ブロック W_j の荷卸しのポート Y_j（荷卸し 15 の開始．「作業ブロックのポート」）に入るエッジは，3種類に分かれる．

| 記号 | 何が満たされる時刻か | 入るエッジ |
|---|---|---|
| a | 台車が接続口に着く | 到着 → 作業（または s からのループの残り時間） |
| b | 先の PJob の TJob の荷卸しが終わる | `precedence` |
| c | conv2^FW(p) に空きができる | `station`（往路の容量の項） |

最長経路では Y_j = max(a, b, c) になるが，実際には，b > a のとき台車は荷卸しに失敗して待たずに周回し，荷卸しできるのは a ＋ kL（L = N_L·t_L^M）のうち b 以後の最初の時刻になる．c（conv2^FW が満杯）のときは，台車は接続口でその場で待つので，max 型のとおりである（後続の台車に押し出されると1周するが，これは無視する）．周回が R 回を超えると再搬送になる（operation_graph.md の「緩和」）．この切り上げと再搬送は，max と足し算だけの最長経路では表せない．

- **グラフ**：max-plus のまま変えない．到着 → 作業のエッジには周回なしの名目値だけを持たせる．エッジを資源（種類）ごとの項で持つので，評価のときに a・b・c を分けて取り出せる
- **評価**：縮約グラフは DAG なので，トポロジカル順に各ノードの時刻を計算できる．作業ブロックのポート Y でだけ，max の代わりに次の規則を使う
  ```
  a = max over 到着→作業（と s）のエッジ,  b = max over precedence,  c = max over 往路の容量
  k* = 0 if b <= a else ceil((b − a) / L)
  if k* <= R:  Y_j = max(a + k*·L, c)
  else:        a' = a + R·L + D_retry(j)    # 再搬送して戻ってくる時刻
               同じ規則を a' で繰り返す（a' は毎回 RL 以上増えるので必ず止まる）
  P_j, Q_j, O_j は，ブロックの中の不等式と入る項の max で求める
  ```
  D_retry(j) は再搬送の名目時間で，作業 34 ＋ 作業 25〜33 ＋ 作業 1〜12 ＋ 13 の処理時間の和（j の置場 (a, f, z) から決まる）
- 規則は a・b・c について単調なので，トポロジカル順の計算にも，作業場の能力と台車を資源として入れた直列化（「後回しにした項目」のシリアル・スケジュール生成法．「実装と運用の方針」の評価）にもそのまま組み込める
- 周回の規則を外せば，max 型の値（楽観的な値）が得られる．両者を比べることもできる．GNN に入力する場合は，グラフをそのまま渡し，代償の推定をモデルに任せることもできる
- 残る近似：再搬送で使うシャトル・リフト・コンベヤの取り合いは無視する（グラフに訪問を足さない）．押し出しによる周回も無視する

代償をエッジの長さとして先に見積もって載せる方式は採らない．b は他のノードの時刻で決まるので，エッジの長さを事前に決められないためである．

### エッジ長の簡略化（L3）

「長さ：剛体近似」で定めた長さ（以下 **L0**）は，定義として残す．運用（ルールベースの評価値，GNN の入力）では，まず L0 をピッキング1回分を単位とする少数の整数に簡略化した長さ（以下 **L3**）を使う．トポロジ（ノード・エッジとその種類）は L0 と同じで，各項の値だけを置き換える．

**目的**：運用効率は主に作業場の稼働率で評価する．作業場 p が遊ばないのは，各作業ブロック W_j への最長路が作業場の鎖（前のピッキングの完了）で決まり，供給側（シャトル・リフト・ループ）の経路で決まらないときである．L3 は，この「作業場側と供給側のどちらが長いか」を，ピッキング何回分という単位で判定できればよい，という考えで作る．GNN には，ノードとエッジの種類を含むトポロジがあれば，長さは近似でも十分と見込む．

#### 単位と区間の重み

**単位**：u ＝ ピッキング時間の代表値 ＋ 2t_C（搬入 17 と搬出 19）を 1 とする．平均（10.8 秒）を代表値とすれば，u ≈ 12.8 秒である．作業場の上で，1つの作業が終わってから次の作業が終わるまでの間隔に当たる．

**区間の重み**：ブロックの作業の列を設備の区間に分け，区間ごとに重み α を与える．α は L0 の平均の処理時間を u で割って丸めたもので，調整用のパラメータとして持つ．

| 区間 | 作業 | L0（秒，デフォルトのパラメータ） | α |
|---|---|---|---|
| シャトル（出庫） | 1〜4 | 2(Z − z)·t_S^M ＋ 2t_S^L → 10.4〜28 | α_S ＝ 2 |
| conv0^FW | 5 | 2 | 0 |
| 往路リフト | 6〜9 | 2f·t_E^M ＋ 2t_E^L → 10〜12 | α_E ＝ 1 |
| conv1^FW | 10 | 4 | 0 |
| ループ（往路） | 11〜13 | t_L^L ＋ 4.6〜14.6（迎車の名目値は，割り付けていなければ 0） | α_L ＝ 1 |
| conv2^FW | 15〜16 | 7 | 0 |
| ピッキング | 17〜19 | u | 1 |
| conv2^BW | 20〜22 | 7 | 0 |
| ループ（復路） | 23 | 4.6〜14.6 | α_L ＝ 1 |
| conv1^BW | 25〜26 | 1 ＋ 4 | 0 |
| 復路リフト | 27〜29（復帰時間を含む） | 10〜12 | α_E ＝ 1 |
| conv0^BW | 30 | 2 | 0 |
| シャトル（入庫） | 31〜33（復帰時間を含む） | 10.4〜28 | α_S ＝ 2 |

- **実行中の区間も丸ごと数える**：残り時間は実際の運用ではわからない（ピッキングの残り時間は作業者しだい）ので，実行中の区間も，残っている区間として α をそのまま数える．実行中のピッキングも 1 とする
- **コンベヤの重みはすべて 0**：conv2 は往復で 14 秒（≈ 1.1u）あるが，他のコンベヤに合わせて 0 とする．作業 → 帰還が L0 より 0.8u 前後短めに出るが，効くのは `bucket` とシャトルの取り合いの時期だけである．コンベヤに正の重みを置くと，同じコンベヤの上で前後に並ぶ TJob の間の項が正になり，流れ作業のコンベヤが1台ずつ処理する機械のように扱われる（例：conv2^BW に3台並ぶと，ピッキング中の TJob まで押し下げられる）ので，これを避ける意味もある
- 復帰時間は，その機械の区間の α に含める
- **迎車**（作業 11・21）：割り付けていなければ 0，割り付けた後は d_L(台車の位置, 接続口)·t_L^M ÷ u を丸めた値（0〜2）．復路の迎車は作業ブロックのポート O の前に入る．クリティカルパスだけで評価するときの w（1周）は L3 で 2 で，下の表の値は，割り付けていない迎車を含むエッジ（到着 → 作業，作業 → 帰還）と D_retry で 2 ずつ長くなる

#### 項の値

L0 の各項 f_B(k) − e_B′(k) の処理時間を，区間の重みに置き換える．

- 入口オフセット ā_B(k)：B に残っている区間のうち，k を使う区間より前のものの α の和
- 出口オフセット b̄_B(k)：ā_B(k) に，k を使う区間自身の α を足したもの
- L3 の項：b̄_B(k) − ā_B′(k)．組の長さは，L0 と同じく資源についての max

これにより，オンライングラフとの対応は L0 のまま保たれる．作業ブロックの中のポートの間は，P ≥ Y，Q ≥ P ＋ 1，O ≥ Q ＋ 迎車（割り付けていなければ 0．クリティカルパスだけで評価するときは w）となる．主な値は次のとおりである（i が先，j が後）．

| 種類・資源 | 組 | L3 の項 |
|---|---|---|
| `station`：作業場 | 作業ブロックどうし（鎖・扇とも） | P_k ≥ Q_i．ブロックの中で Q ＝ P ＋ 1 なので，ピッキングの開始で見て1回分の間隔 |
| `station`：往路の容量 | C₂ 台前 → k | Y_k ≥ P_{k−7} |
| `station`：復路の容量 | C₂ 台前 → k | Q_k ≥ O_{k−7} |
| `station`：復路の順序 | 直前 → k | O_k ≥ O_{k−1}（L0 の t_L^L は 0 に丸める） |
| `precedence` | 作業ブロックどうし | 0（L0 は t_L^L ≈ 0.08u．順序を表す種類として残す） |
| `aisle`：シャトル（出庫どうし） | 到着 → 到着 | 2 |
| `aisle`：往路リフト | 到着（conv0・リフト）→ 到着（conv0） | 1 |
| | 到着（conv0・リフト）→ 到着（置場） | −1 |
| `aisle`：conv0^FW・conv1^FW のセル | 同じコンベヤで前後 | 0 |
| | 前がコンベヤ，後が上流（リフト・conv0・置場） | −1〜−3 |
| 復路の機械：復路リフト | 帰還 → 帰還 | 1 |
| 復路の機械：シャトル（出庫 → 入庫，入庫どうし） | → 帰還（復路リフトを降りる前） | 1 |
| | → 帰還（復路リフトを降りた後） | 2 |
| 復路の機械：シャトル（入庫 → 出庫） | 帰還 → 到着 | 2 |
| 復路の機械：conv1^BW・conv0^BW のセル | 往路のセルと同じ | 0 または負 |
| `bucket` | 帰還 → 到着（順番待ち） | 帰還ブロックに残っている重みの和（最大 3） |

- **負の項はそのまま持つ**：L0 と同じく「これだけ先に出発してよい」という余裕を表す．s → B（長さ 0）と並ぶので，ふつうは効かない．0 で切ると，L0 にない制約を加えることになる
- `bucket` の項は，同じシャトルの「入庫 → 出庫」の項と同じ値になる．したがって `bucket` が効くのは，シャトルでの順序がまだ決まっていない間である

#### 同じ TJob のブロックの間のエッジと開始エッジ

| エッジ | L3 | L0 の平均 ÷ u |
|---|---|---|
| 到着 → 作業（置場から） | α_S ＋ α_E ＋ α_L ＝ 4 | 3.7 |
| 到着 → 作業（conv0・リフトから） | α_E ＋ α_L ＝ 2 | 2.1・1.6 |
| 到着 → 作業（conv1 から，台車を割り付けていない） | α_L ＝ 1 | 1.0 |
| 到着 → 作業（conv1 から，台車を割り付け済み） | 迎車（0〜2）＋ α_L | ― |
| s → 作業（ループ上） | α_L ＝ 1 | 0.4〜0.8 |
| 作業 → 帰還（ピッキング前） | 1 ＋ α_L ＝ 2 | 2.8 |
| 作業 → 帰還（ピッキング中） | 2 | 1.8〜2.3 |
| 作業 → 帰還（ピッキング後，台車を割り付けていない） | α_L ＝ 1 | 1.3 |
| 帰還（再帰還）→ 到着 | 残っている重みの和（最大 3） | 2.9 |

作業 → 帰還の値は，作業ブロックの先頭からポートの間を通って帰還ブロックに着くまでの和である（ポートの間で待たない場合）．

- **開始エッジ**：s → B ＝ 0 の1種類だけとする．復帰中の機械からの開始エッジ（残りの復帰時間．最大でシャトル 9 秒 ≈ 0.7u，復路リフト 1 秒）は 0 に丸め，s → B と重なるので張らない．このとき TJob のブロックはもう消えているので，「実行中の区間を丸ごと数える」原則は当てない
- 稼働率の観点では，「置場にある TJob は，作業場で実行中の作業のほかに4回分以上の作業が並んでいれば間に合う」と読める（置場からピッキングの開始までが 4．台車を待つ時間は直列化で加わる）
- 検算：同じバケットを続けて使う i → j は，i が作業場に着いてから j が作業場に着くまでを，作業 → 帰還 2 ＋ `bucket` 3 ＋ 到着 → 作業 4 ＝ 9 とする．L0 の平均は約 120 秒（9.4u）である

#### 作業ブロックの時刻の読み方

作業ブロックのポートのうち，Y_j は conv2 への到着（荷卸し），P_j はピッキングの開始（の直前の搬入）である．L0 でも P_j はピッキングの最早開始時刻を直接表し，固定のバイアスはない（ポートを入れる前の剛体近似では，ブロックの時刻 ＝ ピッキングの開始 − 8 秒だった）．L3 では P_j がそのままピッキングの開始時刻になる．

到着側の見積りは，評価の規則の a（到着 → 作業のエッジ，または s からのループの残り）として取り出せる．

- P_j − (Y_j ＋ d_FW) ＞ 0：j は早めに着いて conv2^FW の上で待つ．作業場への供給は足りている（差は供給の余裕）
- P_j ＝ Y_j ＋ d_FW で，Y_j ＝ a（a が効いている）：作業場は j を待って遊びうる
- Q_j − (P_j ＋ ピッキング) ＞ 0：搬出が conv2^BW の満杯で待たされている（作業場の閉塞）

これらの差は，作業場の稼働率をみる指標として使える．

#### 評価の規則の定数

「周回・再搬送の代償（評価の規則）」の形はそのままで，定数を L3 の単位にする．

| 定数 | L0 | L3 |
|---|---|---|
| 周回 L | N_L·t_L^M ＝ 20 秒（1.56u） | 2 |
| 再搬送 D_retry | 置場の位置 (a, f, z) で変わる（平均 約 94 秒，7.3u） | 作業 34（α_L ＝ 1）＋ 再帰還（3）＋ 到着 → 作業（4）＝ 8（位置によらない） |
| 周回の上限 R | 回数 | そのまま |

```
k* = 0 if b <= a else ceil((b − a) / 2)
if k* <= R:  Y_j = max(a + 2·k*, c)
else:        a' = a + 2R + 8        # 再搬送して戻ってくる時刻．同じ規則を a' で繰り返す
```

- `precedence` が 0 なので，b は先の PJob の TJob の荷卸しのポート Y そのものである．b ＝ a なら周回しない
- 長さが整数なので，タイがよく出る．タイは周回なしの側（楽観側）に倒れる．丸め（実行中の区間を丸ごと数えるなど）は悲観側に出やすいので，向きが逆で打ち消し合う傾向がある

#### 現実装（1ノード縮約）の長さとの違い

現実装もピッキング1回を単位とし，設備ごとの α（`loop`・`lift`・`shuttle`）を持つ点で，L3 と同じ考え方である．主な違いは次のとおりである．

- コンベヤで隣り合う TJob の間：現実装は 1，L3 は 0（conv1 の行列は，台車が来れば1台あたり t_L^L で掃ける）
- `precedence`：現実装は 1，L3 は 0（ピッキングの間隔は `station` の項が持つ）
- `bucket`：現実装は β（初期値 1），L3 は帰還ブロックの残りの重み（最大 3）．バケットを置場に戻して出し直す時間を反映する
- L3 では負の項が出る（現実装はすべて 0 以上）

### 実装と運用の方針

**オンライングラフは実運用では持たない**．オンライングラフも縮約グラフも，時刻 t のシミュレータの状態（各 TJob の位置と進捗，ディスパッチで確定した割付け，台車の位置）から一意に決まる．縮約グラフは状態から直接作れるので，オンライングラフは定義と検証のための基準として使う．

**実装の順序**（往路だけを先に実装することはしない）：

1. **参照実装**：時刻 t の状態から，作業レベルのオンライングラフ（往路と復路，`unrestored_tjobs` 全体）を作り，定義どおり機械的に縮約する．速さは問わない．次の3つを確かめる
   - 縮約グラフが DAG であること【確認済み（2026-11-25）：`gtp/reduction.py`．ブロック単位のトポロジ，ポートに分けたグラフ（L0・L3），ポートなしのグラフ（L0・L3）．6条件の一定間隔の時点】
   - オンライングラフの最早開始時刻が，実際の時刻以下であること（下界の性質）【確認済み（2026-11-25）】`gtp/operation_graph.py`．一定間隔の時点（5条件）とディスパッチの時点（12条件．台車数・`RELEASABLE` を変えたものを含む）で，移載を伴うすべての作業について成り立つ（ピッキングは実現値）
   - 縮約グラフの時刻と実際の時刻のずれ（剛体近似の誤差）
   - ポートの有無によるずれの違い（ポートは切り替えられるようにしておく．未決事項13）
   - L3 の長さと L0 の長さの差（「エッジ長の簡略化（L3）」）
   - 参照実装の前に確かめること：(i) シミュレータの状態からオンライングラフ（各機械の鎖と扇，名目値）を読み取る対応（tjob_lifecycle.md と現行の位置の分類を使う），(ii) 検証に使う実際の時刻の取り方．【対応済み（2026-11-24）】`models.py` に，イベントと乱数の順序を変えない範囲で次を加えた（golden test は不変）．実行中の機械の TJob は `cell.assigned_tjob`，実行中の作業の残り時間は `cell.hold_end`，荷卸し失敗の回数は `tjob.failure_count`，ブロック・ポート単位の実績の時刻は `tjob.history` から読む（tjob_lifecycle.md の「時刻の記録」）．(i) の機械ごとの対応づけはこれを前提に行う
2. **直接構築**：位置の分類から，各組のオフセットを直接計算する速い実装．参照実装と一致することをテストで確かめる【完了（2026-11-25）：`gtp/block_graph.py`．「直接構築の手順」】
3. **評価**：周回・再搬送の規則と，作業場の能力と台車（V 台．空く時刻と位置で持ち，迎車をその場で計算する）を資源として入れた直列化．台車を待つ時間はここで入れる（未決事項12）

往路だけで始めない理由：

- 長さはどのブロックでも同じ式で計算するので，復路で増えるのは作業の列のひな形（19〜33）と，復路にいる TJob の位置の分類だけである
- 往路だけにすると，`bucket` の始点（作業 33）の代用という使い捨ての規則が要る．また，シャトルでの入庫との取り合いや，conv2^BW の詰まりという実在する制約が抜けるので，実際の時刻とのずれが剛体近似の誤差によるものかどうかを切り分けられない

**運用時の更新**：

- **方式1（当面）**：ディスパッチのたびに状態から作り直す（現行の `TJobGraph.update()` と同じ形）
- **方式2（速さが問題になったら）**：差分で更新する．オンライングラフの更新操作は，次のブロック単位の操作に置き換わる

縮約グラフのエッジの長さ ℓ′(B, B′) は，（組，資源）ごとの**項** f_B(k) − e_B′(k) の max である（「オフセットの形」）．オンライングラフの1本のエッジ（機械順序エッジの鎖・扇，作業場順序エッジ，バケットエッジ）が1つの項になり，扇1つは同じ資源の，行先ごとの項の束になる．差分の更新は，この項の追加・削除として書ける．

| オンライングラフの操作 | 縮約グラフでの操作 |
|---|---|
| U1 扇の張り替え | 資源 k の項のうち，末尾 i → 未確定のブロック（c 以外）を外し，c → それらを加える．i → c の項はそのまま（扇から鎖に変わるだけで長さは同じ） |
| U2 鎖の追加 | 新しい TJob のブロックを加え，各資源の末尾から項を張る |
| U3 挿入 | 周回は到着 → 作業のエッジ（または s → 作業）の長さを変えるだけ．再搬送は，再帰還ブロックと新しい到着ブロックを加える |
| U4 削除 | 完了した資源の項を外し，s → B の長さを更新する．ブロックの作業がすべて完了したらノードを消す |
| U5 処理時間 | 該当するブロックのオフセット（台車の迎車など）と，その項を持つエッジだけを計算し直す |

方式2に備えて，次のように持つ．

- **エッジは（組，資源）ごとの項で持つ**：組の長さは資源ごとの差の max なので，max をとった1本だけを持つと，扇の張り替えで1つの資源の項を外したいときに，残りを復元できない．max は評価のときにとる．エッジの種類は資源から決まるので，GNN にも種類つきで渡せる
- **オフセットは固定の原点から測る**：ブロックができたときの先頭の作業を原点とし，作業が完了しても原点を動かさない．s → B の長さ（−d(原点, 今の先頭)）だけを更新すれば，作業の完了は「使い終えた資源の項を外す」だけで済む
- 資源ごとに「鎖の末尾のブロック」と「未確定のブロックの集合」の索引を持つ（状態から読めるので，オンライングラフは要らない）
- 作業ブロックはポートを持ち，過ぎたポートとそこに出入りする項は U4 で取り除く

### 直接構築の手順

`gtp/block_graph.py` の `BlockGraph` が，作業を展開せずに，参照実装（`Reduction`，ポートあり）と同じ項を作る（方式1．毎回スクラッチから）．

1. **状態を読む**：`gtp/state.py` の `StateReader`．各 TJob の最初の未完了の作業（作業番号，セル番号，残り時間）と，確定した順（conv0^FW・conv1^FW・作業場・復路）．オンライングラフ（`OnlineGraph`）と共有する
2. **ブロックを作る**：先頭の作業と残り時間だけを持つ．ループの上（13・14・23・34）の TJob は，s からの長さを持たせる
3. **オフセット**：作業の開始の累積 C は，ブロックの型と置場（階・段）で決まるので，表にして使い回す．先頭の作業 h の残り時間を rest とすると，base ＝ C(h) ＋ p(h) − rest（未着手なら C(h)）で，作業 v の開始は C(v) − base，終了は C(v) ＋ p(v) − base．割り付けた後の迎車（11・21）と実行中のピッキング（18）は，必ずブロックの先頭で実行中なので，rest として入る
4. **資源ごとの項**：資源を使う最初と最後の作業を持ち（`Usage`），f ＝ 最後の作業の終了 ＋ 復帰時間，e ＝ 最初の作業の開始．確定した列の隣どうしに鎖，末尾から扇を張る．扇の先は，階ごとのブロックの索引から取る
5. **作業場と conv2**：確定した作業場の順の中で，lag 台前のポートから張る（作業場と復路の順序は 1，容量は C₂）
6. **L3**：項を張る組は同じで，オフセットを，残っている区間の重みの和に置き換える

**検証**：L0 は値の差 1e-9 以下，L3 は完全一致で，ノードと全項が参照実装と一致する（`tests/test_block_graph.py`．6条件の一定間隔の時点と，3条件のディスパッチの時点）．状態の読み取りは共有なので，その誤りは一致では見つからない．読み取りは，実績との照合（`tests/test_operation_graph.py`）が守る．

### 1ノード縮約（現行実装）との関係

- オンライングラフは閉路を持たない（実際のスケジュールがすべての制約を満たし，エッジの長さが正であるため）．現行実装の閉路（「閉路の性質」）は，ループの上流の作業（`aisle` がかかる 1〜12）と下流の作業（`precedence` と conv2 の扇がかかる 15〜）を1点にまとめたことで生じたものである
- 「後回しにした項目」にあった「到着と作業を分ける案」は，この縮約の到着ブロックと作業ブロックとして導かれる．その案で未決だった論点には，次のように答えが出る
  - `station` の上流へのエッジ：往路の容量の項として，作業ブロックのポート Y につなぐ（「作業ブロックのポート」）
  - 追い越しの代償：U3 の挿入先が到着 → 作業の間なので，そこで扱う．グラフは max-plus のまま，評価の規則で周回の切り上げと再搬送を入れる（「周回・再搬送の代償（評価の規則）」）
  - `bucket`：終点は j の到着ブロック（作業 1）で，作業ノードどうしではない
- 現行実装の「境界の数・α・β」は，オフセットの差を単位時間で粗く数えたものと解釈できる．縮約の定義では長さを名目の処理時間から計算できるので，α・β は「名目値を置き換える係数」という位置づけになる
- 現行実装の骨格（位置の分類，エッジの種類，向き，長さの内訳を属性に持たせる方式）は残せる見込みで，変わるのはノードの構成と長さの付け方である

| 6 | 【解決】直接構築のアルゴリズム | 位置の分類から各組のオフセットを直接計算する手順を書き，参照実装との一致をテストで確かめる（実装の順序の2）．結果は「直接構築の手順」 |
| 7 | 【整理済み】現行定義との差分 | `aisle` の木構造（リフト → 各階の conv0 → シャトル → 置場）とリフトの扇（末尾から全階の未確定の訪問へ）の違い，`station` の扇の先に順番待ちの TJob が入ること．「直接構築の手順」の「現行実装との違い」にまとめた．現行実装（`gtp/graph.py`）を置き換えるかは未定 |

| 10 | ディスパッチ候補の評価 | ルールベースでディスパッチの評価値を出すときに，候補ごとに仮のグラフを作って比べる方法．(i) その差し立ての U1（と連鎖）だけを項の入れ替えで反映し，s からの最長路を差分で計算し直す（軽いが，未確定の順序どうしの競合を数えない），(ii) 残りの順序も基準の規則で決めきって架空の事後グラフを作る（ロールアウト．重いが競合を数える）．ループのディスパッチは U1 を起こさないので，「周回・再搬送の代償（評価の規則）」を候補ごとに当てる．GNN で使う場合は不要 |
| 11 | 【方針決定】コンベヤのバッファの表し方 | 作業ブロックの中にポート（Y・P・Q・O）を持たせ，conv2 のセルの項を容量・順序の項に置き換える（ブロックの粒度は変えず，評価に使うグラフの実体では作業ブロックが4ノードに分かれる．項は 0 以上の定数になる．「作業ブロックのポート」）．到着・帰還ブロックの conv0・conv1 には**今は広げない**（2026-11-25．到着・帰還の時刻 A・R の縮約による平均誤差の差が 1.1 秒以下と小さいため）．直接構築の手順に反映済み |
| 12 | 台車を待つ時間の扱い | 迎車（作業 11・21）の名目値は台車を割り付けるまで 0 で，台車の台数の不足も表さない（オンライングラフの緩和）．【方針決定】グラフの名目値は 0 のままとし，台車を待つ時間は評価の直列化で台車を資源として扱って入れる（台車を「空く時刻と，そのときの位置」で持ち，迎車 ＝ 空いた位置から接続口までの距離 × t_L^M）．直列化では，割り付けていない TJob の迎車も台車の空き具合から決まるので，差し立てた台車の迎車がそれより長ければ，その差し立てが悪いという本当の情報になる．クリティカルパスだけで評価する場合に限り，w ＝ 1周に置き換えるパラメータを持つ（「作業ブロックのポート」）．残り：直列化での台車のモデルの詳細（押し出しによる周回（作業 24）で台車がふさがることの扱いを含む） |
| 13 | 【測定済み】ポートの有無による比較 | 参照実装でポートを切り替えられるようにし，作業ブロックを剛体のまま（ポートなし）にした場合と，ポートを入れた場合の両方を計算して，実際の時刻（検証用に記録するブロック・ポート単位の時刻）と比べる．見る量は，作業場の解放 Q・ピッキングの開始 P・荷卸し Y（周回の判定）・台車への到達 O．見込みは，O はほとんど変わらず，ずれは上流（Q・P・Y）に台車待ちの時間の程度で出ること（「作業ブロックのポート」）．台車の台数や `RELEASABLE` を変えて，混雑の度合いとの関係も見る．同じ比較を到着・帰還ブロックの conv0・conv1 のポートにも行い，広げるかどうか（11 の残り）を決める．8 の誤差の測定の一部として行う．結果は「参照実装による誤差の測定」．conv0・conv1 のポートの比較は行っていない（11 の残りを参照） |

## エッジの向き

すべてのエッジは **「先にピッキング作業を行える TJob → 後に回される TJob」** の向きに張る．

- 経路順序：作業場に近い（下流の）TJob → 遠い（上流の）TJob
- 先行関係：先の PJob の TJob → 後の PJob の TJob

両者が食い違う箇所（例：後の PJob の TJob が，先の PJob の TJob より経路上で前にいる）は閉路として現れる．構築時には閉路をそのまま残す．

---

## ノード

| ノード | キー | 説明 |
|---|---|---|
| スタート | `('start',)` | ダミー．1つだけ |
| アイドル作業場 | `('station', p)` | 作業場 p が作業中でないときのダミー |
| TJob | `('tjob', pjob.idx, tjob.idx)` | 対象範囲（`unpicked_tjobs`）の TJob |

作業場 p が作業中の場合は，作業中の TJob のノードが作業場ノードを兼ねる（アイドル作業場のダミーは作らない）．

### TJob の位置

各 TJob の位置は，**物理的な所在**（`tjob.bucket.cell`）で決める．割付け済みでもバケットを積む前（空車で迎えに行っている途中など）は，バケットの所在で判断する．設備（コンベヤ・リフト・シャトル・台車）は，TJob を積んでいるときだけその TJob のノードとして現れ，空の設備に対応するノードは作らない．

| 位置 | 該当する TJob |
|---|---|
| `station` | 作業場 p にバケットがあり，ピッキング作業中 |
| `conv2` | 作業場 p の入口コンベヤ（stage 2，出庫）上 |
| `car` | ループ台車に積まれた出庫ジョブ（`ON_FW_LOOP`） |
| `conv1` | 系列 a のループ入口コンベヤ（stage 1，出庫）上 |
| `lift` | 系列 a の出庫リフトに積まれている |
| `conv0` | 系列 a・階層 f のリフト入口コンベヤ（stage 0，出庫）上 |
| `shuttle` | 系列 a・階層 f のシャトルに積まれた出庫ジョブ |
| `store` | `TO_FW_SHTL` で，バケットが置場にある |
| `beyond_store` | 再搬送のため入庫経路を戻っている（`retry_needed == True`） |
| `off_route` | バケットの順番待ち（`bucket.current_tjob()` が自身でない） |

`station` から `store` までは，バケットの現在のジョブ（`bucket.current_tjob()`）である TJob に限る．再搬送中の TJob を積んだシャトル・台車は，出庫経路の上では空として扱う．

## エッジ

### 種類

| `kind` | 張り方 |
|---|---|
| `start` | S → 各作業場ノード |
| `station` | 同じ作業場行きの TJob 間（作業場から conv2・台車・ループより上流へ） |
| `aisle` | ループより上流で，同じ系列の経路上で隣り合う TJob 間（空の設備は飛ばす） |
| `precedence` | 同じ作業場の，隣り合う PJob の TJob 間 |
| `bucket` | 同じバケットで，割付け順に隣り合う TJob 間 |

`station` は作業場を共有することから，`aisle` は系列（コンベヤ・リフト・シャトル）を共有することから来る順序関係を表す．

### `station`：同じ作業場行きの TJob 間

作業場 p ごとに，下流から上流へ次のように結ぶ．

```
作業場 p → conv2 の TJob（下流から順に直列）→ 作業場 p 行きの TJob を積んだ台車（並列）
                                          → ループより上流にある作業場 p 行きの全 TJob（並列）
```

- 台車とループより上流の TJob へは，いずれも **conv2 の最上流の TJob**（conv2 が空なら作業場ノード）から張る
- ループでは追い越しが起こりうるので，台車上の TJob からループより上流の TJob へはエッジを張らない
- ループより上流の対象は，全系列の `conv1`・`lift`・`conv0`・`shuttle`・`store`・`beyond_store` にある作業場 p 行きの**すべての** TJob とする

同じ系列上で `aisle` でたどれる TJob への `station` エッジは冗長になりうるが，最長経路長には影響しないので絞り込まない．

### `aisle`：同じ系列の TJob 間

系列 a ごとに，下流から上流へ次の順に結ぶ．合流点では並列に分岐する．行先の作業場に関係なく張る．

```
conv1 の TJob（下流から順に直列）→ 出庫リフト → 各階層 f の conv0 の TJob（並列に分岐，各々下流から順に直列）
  → シャトル → 置場待ちの TJob（並列）
             → 置場の向こう側の TJob（並列）
```

置場の向こう側の TJob は，置場待ちの TJob と同じ起点から張る（置場待ちの TJob から張るのではない）．系列の鎖は，`station` エッジを通してのみ作業場側とつながる．

### 空の設備の飛ばし方

途中の設備が空の場合は，それを飛ばして次に TJob がある位置に直接エッジを張る．たとえば出庫リフトが空なら conv1 の最上流の TJob から各階層の conv0 の最下流の TJob へ，conv0 も空ならシャトルへ，と順にたどる．

### `precedence`

同じ作業場に割り付けられた PJob を `pjob.idx` の順に並べ，隣り合う PJob の TJob 間に，すべての組み合わせでエッジを張る．対象範囲の TJob を1つも持たない PJob は飛ばす．同じ PJob 内の TJob 間にはエッジを張らない．

### `bucket`

同じバケットに割り付けられた未完了の TJob（`bucket.undone_tjobs()`）を割付け順に並べ，隣り合う TJob 間にエッジを張る．

## エッジの長さ

### 境界の長さ

`station`・`aisle` の長さは，始点の位置から終点の位置まで上流へたどる間に越える境界の長さの合計とする．

| 越える境界 | 長さ |
|---|---|
| コンベヤ上で隣り合う TJob 間（作業場 → conv2 の最下流の TJob を含む） | 1 |
| 下流 → 台車（台車の出口側） | 1 |
| 台車 → 上流（台車の入口側） | α（設備の種類ごと：`loop`・`lift`・`shuttle`） |
| 置場 → 置場の向こう側 | β |

- 空の設備を飛ばしても，境界の合計は設備がある場合と一致する（例：空のリフトを飛ばす conv1 → conv0 のエッジは 1 + α_lift）
- 空のコンベヤは境界の長さに何も加えない（例：conv0 が空のとき，リフト → シャトルのエッジは α_lift + 1）
- `station` のループより上流へのエッジは，途中の台車を空とみなして飛ばし（台車の出口側の 1 と入口側の α_loop を加える），その先は設備の境界のみを数えて途中にいる TJob の分は加えない（例：conv2 の最上流 → シャトル上の TJob は 1 + α_loop + 1 + α_lift + 1）．台車上に TJob があっても長さは変わらない

### 種類ごとの長さ

| `kind` | 長さ |
|---|---|
| `start` | 0 |
| `station`・`aisle` | 境界の長さの合計 |
| `precedence` | 1 |
| `bucket` | β |

基準の時間単位（1）はピッキング作業時間のイメージ．α・β は調整用のパラメータで，初期値はすべて 1 とする．

### 長さの内訳の持たせ方

① 構築では長さを確定させず，各エッジに内訳を属性として持たせる．

| 属性 | 意味 |
|---|---|
| `kind` | エッジの種類 |
| `n_unit` | 長さ 1 の境界の個数 |
| `alphas` | 越えた台車の入口側の種類のリスト（例：`['loop', 'lift']`） |
| `n_beta` | β の個数 |

長さ ＝ `n_unit` ＋ Σ α[`alphas` の各要素] ＋ `n_beta` × β として ② で計算する．`precedence` は `n_unit = 1`，`bucket` は `n_beta = 1`，`start` はすべて 0 となる．

---

## グラフの型

`networkx.MultiDiGraph` を用いる．同じノード対の間に種類の異なるエッジ（例：`station` と `precedence`）が重なりうるため．エッジのキーは種類（`kind`）とする（例：`graph.has_edge(u, v, key='station')`）．

## 閉路の性質

> この節は，1つの TJob を1ノードにまとめる現行実装についての記録である．縮約の定義（到着ブロックと作業ブロックを分ける）では，この閉路は構造的に生じない（「閉路がないこと」「1ノード縮約（現行実装）との関係」を参照）．

構築したグラフには閉路が現れうる．その構造について，次のことが言える．

### 結論

- **作業場・conv2 の TJob は閉路に入らない**．閉路に入りうるのは台車・ループより上流（`conv1`〜`beyond_store`）・順番待ち（`off_route`）の TJob
- **どの閉路にも，到着順が減る向きの `aisle` エッジと，`precedence` エッジが必ず含まれる**．`bucket` は途中に入ることがあるが必須ではない．`start`・`station` は閉路に入らない
- したがって，どの閉路にもループより上流の TJob が含まれる．台車・順番待ちの TJob が閉路に入るのは，その閉路の途中を通る場合に限られる

閉路は，物理的な前後関係（`aisle`）と作業場での作業順（`precedence`）が食い違うことで生じる．`bucket` は，作業場をまたいでその食い違いを伝える役割を担うだけである．

### 根拠

**作業場・conv2 の TJob が閉路に入らない理由**．台車から作業場の入口コンベヤへの荷卸しは，同じ作業場の先の PJob のすべての TJob が台車より先に進み，かつ再搬送中でないときだけ行われる（`TJob.late_preceding_tjob_count()`）．ここから次の2つが言える．

1. 作業場・conv2 の中は，作業場から上流へ向かって `pjob.idx` が減らない順に並ぶ（コンベヤは追い越しのない FIFO）．そのため，中の `station`・`precedence` エッジはどちらも上流へ向かう一方通行になる
2. 作業場・conv2 の TJob に外から入るエッジはない．`station` エッジは作業場ノードから conv2 をたどるだけである．`precedence` の始点となる先の PJob の TJob は，すでに作業場・conv2 にいるか，ピッキング済みでグラフにいない．`bucket` の終点は順番待ちの TJob だけである

**台車上の TJob が閉路に入りうる理由**．台車に積む段階の先行関係の確認はソフトな制約で（`DefaultController.precedence_filter()`），制約を満たしていなくても積まれることがある．台車上の TJob には `precedence` が出入りするので，閉路の途中を通りうる．

**`aisle` と `precedence` が必須である理由**．各 TJob に到着順を表す組 `(pjob.idx, tjob.idx)` を割り当て，辞書式に比べる．

- `precedence` は，同じ作業場で `pjob.idx` が増える向きにしか張らない
- `bucket` も組が増える向きにしか張らない．PJob は `pjob.idx` の順に投入され（`dispatch_pjobs()` の仕様），TJob は投入時に `tjob.idx` の順に作られて，バケットの `tjobs` の末尾に追加されるため．再搬送になっても順番は入れ替わらない（現在のジョブは未完了の TJob の先頭）
- `aisle` だけでは閉路はできない．系列ごとに下流から上流への一方向に張り，枝分かれはするが合流しないため

閉路を一周すると組は元に戻るので，組が減る向きのエッジが必要になる．そうなりうるのは `aisle` だけである．また，`bucket` の終点は順番待ちの TJob である．順番待ちの TJob からは `precedence`・`bucket` しか出ないので，上流側へ戻るには `precedence` を通るしかない．そのため，`aisle` と `bucket` だけの閉路もできない．

この結論は，PJob を `pjob.idx` の順に投入することに依存する．投入順を入れ替えるコントローラでは成り立たない．

### スナップショットでの確認

時間1ごとのスナップショットで，閉路のある時点のグラフから各種類のエッジを除き，閉路が解消するかを調べた．

| 条件 | 閉路のある時点 | `precedence` を除く | `aisle` を除く | `bucket` を除く |
|---|---|---|---|---|
| `PJOB=50, SEED=42` | 52 | 52 で解消 | 52 で解消 | 0 で解消 |
| `PJOB=50, SEED=1, OPENABLE=1` | 165 | 165 で解消 | 165 で解消 | 42 で解消 |
| `PJOB=100, SEED=1234` | 221 | 221 で解消 | 221 で解消 | 0 で解消 |

あわせて，3条件とも，作業場・conv2 の TJob は一度も閉路に入らなかった．また，`precedence`・`bucket` に組が減る向きのエッジは1本もなかった．

### precedence と矛盾する `aisle` の列

閉路の中で `aisle` エッジが連続する極大な区間を「`aisle` の列」と呼ぶ．列の中に同じ作業場行きの TJob が2つあり，下流側のほうが後の PJob であるとき，その列は precedence と矛盾するという．

- **閉路に含まれる `aisle` の列は1つとは限らない**．2つ以上の閉路もふつうに現れる
- **閉路の `precedence` がすべて1つの作業場 p のもので，`bucket` を含まなければ，precedence と矛盾する列が少なくとも1つある**．各列の両端はどちらも作業場 p 行きの TJob であり，`precedence` の区間を通るたびに `pjob.idx` は増える．一周して元に戻るには，どこかの列で `pjob.idx` が減らなければならない
- **複数の作業場にまたがる閉路では，矛盾する列がないことがある**．どの列も1つの作業場の中では矛盾していないが，複数の系列での前後関係を組み合わせると，作業場どうしが互いに相手を待つ形になる

例（`PJOB=50, SEED=42`，時刻19．括弧内は位置，行先作業場，系列）：

```
17-0（conv0，p2，系列1）  → precedence →
22-2（リフト，p2，系列3）  → aisle →
4-0（conv0，p4，系列3）    → precedence →
9-0（conv0，p4，系列5）    → precedence →
14-0（リフト，p4，系列1）  → aisle →
0-0（シャトル，p0，系列1） → aisle →
7-0（置場，p2，系列1）     → precedence →
12-0（リフト，p2，系列2）  → aisle →
12-1（シャトル，p2，系列2）→ precedence → 17-0 に戻る
```

作業場 p2 は 22 より前に 7 を済ませる必要があるが，7-0 は系列1で p4 行きの 14-0 の後ろにいる．作業場 p4 は 14 より前に 4 を済ませる必要があるが，4-0 は系列3で p2 行きの 22-2 の後ろにいる．

長さ10以下の閉路を1時点あたり最大300個まで列挙して分類した結果（すべての閉路を数えたものではない）：

## 実装（`gtp/graph.py`）

| 名前 | 説明 |
|---|---|
| `TJobGraph(gtps, scope='unpicked')` | グラフ構築器．`scope` は現在 `'unpicked'` のみ |
| `TJobGraph.update()` | 現時点の状態からグラフを構築して返す（毎回スクラッチから構築） |
| `edge_length(data, alpha=None, beta=None)` | エッジ属性の内訳から長さを計算する．省略時は `DEFAULT_ALPHA`・`DEFAULT_BETA`（すべて 1） |
| `tjob_key(tjob)`・`START` | ノードのキー |

ノード属性は `node_type`（`'start'`・`'station'`・`'tjob'`）のほか，TJob ノードには `position`・`picker`（行先作業場）・`pjob`・`progress`（int）・`aisle`・`floor`（置場の系列・階層）・`retry_needed`・`tjob`（元の `TJob` への参照）を持たせる．アイドル作業場ノードは `picker` を持つ．

構築処理は設備側から走査して各 TJob の位置を分類し，各位置で `progress` が想定どおりであることを `assert` で確認する．`random` は呼ばないので，グラフを使ってもシミュレーション結果は変わらない（`tests/test_graph.py` で golden 値により確認）．

観察用に `examples/inspect_tjob_graph.py`（引数：構築する時刻）があり，位置別ノード数，種類別エッジ数，サイズ2以上の強連結成分を表示する．
描画用に `examples/show_tjob_graph.py` があり，ノードを位置ごとの段（縦），作業場・系列・階層ごとの列（横）に並べて PNG に保存する（既定の保存先は `data/tjob_graph_t<時刻>.png`）．ノードの色は行先作業場，赤枠は閉路（サイズ2以上の強連結成分）に含まれるノード，`*` は再搬送中を表す．`--kinds` で描くエッジの種類を絞れる（閉路の判定は描かないエッジも含むグラフ全体で行う）．

```bash
uv run examples/show_tjob_graph.py --time 200                                    # 全種類のエッジを描画
uv run examples/show_tjob_graph.py --time 200 --kinds start,station,precedence,bucket  # aisle を除いて描画
```

**計測値（参考）**：`PJOB=100, SEED=1234` で，ディスパッチのたびに構築すると（838回）1回あたり約 0.27 ms，実行時間は約 0.41 秒から約 0.64 秒（約1.5倍）になった．エッジの種類を `station`・`aisle` に再整理する前（台車から上流へ `direct` を張っていた版）は，1回あたり約 0.32 ms，約 0.68 秒だった．

## 後回しにした項目

> 次の2項目は，縮約の定義（「オペレーショングラフからの導出（縮約）」）で解消した．経緯として要点だけを残す．

- **【解消】最長経路長の計算時の閉路の扱い**：現行実装（1ノード縮約）では閉路が生じるので，到着順が減る向きの `aisle` エッジや閉路の中の `precedence` エッジを除く規則を検討していた．縮約の定義では到着ブロックと作業ブロックが分かれるので，閉路は構造的に生じず（縮約の「閉路がないこと」），閉路を除く操作は不要になった
- **【解消】追い越しを仮定して，到着と作業を分ける案**：ループより上流の各 TJob を到着ノード（`aisle` が結ぶ）と作業ノード（`station`・`precedence` が結ぶ）に分ける案．現行のグラフから構造だけを分割した試作（`uv run examples/split_tjob_graph.py`）では，閉路のあった時点（`PJOB=50, SEED=42` で 52，`PJOB=50, SEED=1, OPENABLE=1` で 165，`PJOB=100, SEED=1234` で 221）のすべてで閉路がなくなった．この案は縮約の到着ブロックと作業ブロックとして導かれ，未決だった論点（`station` の上流へのエッジの接続先，追い越しの代償の載せ先，`bucket` の端点）も縮約の定義で答えが出た（「1ノード縮約（現行実装）との関係」）．追い越しの代償（周回・再搬送）の見積り方は，縮約の未決事項3として残る
- **作業場の能力を考慮した開始時刻の見積り**：スタートからの最長経路長は，作業場の能力を無視した最早開始時刻（ES）とみなせる．同じ作業場では複数の TJob を同時に作業できないので，縮約グラフ（DAG）に対して，最長経路の計算と作業場ごとの直列化を1回の走査で同時に行う（シリアル・スケジュール生成法）
  ```
  トポロジカル順（同順位は ES などの優先度順）に TJob v を取り出し，
    s[v] = max( max_{u→v} (s[u] + len(u,v)),  free[p(v)] )
    free[p(v)] = s[v] + 1        # p(v): v の行先作業場，作業時間は 1
  ```
  - 「ES を求めてから作業場ごとに昇順に並べてずらす」2段階の方法は採らない．作業場内は整合するが，ずらした分が作業場をまたぐエッジ（`bucket`・`aisle`）の先に伝わらないため
  - ずらす量は同点のときに限らず，前の TJob の終了時刻で押し下げる（α・β が 1 以外だと ES は整数とは限らないため）
  - 作業中の作業場は，作業中の TJob を開始時刻 0，作業場の空き時刻を 1 から始める（残りの作業時間を使うかは後で選ぶ）
  - 同点の順は `pjob.idx`，`tjob.idx` の順として結果を一意にする
  - 拡張：シャトル（系列・階層ごと）・リフト（系列ごと）の空き時刻も持たせれば上流の詰まりも反映できる．まず作業場のみで始め，効果を見て判断する
  - 縮約の定義では長さが名目の処理時間になるので，作業時間 1 は作業ブロックの処理時間（ピッキングの名目値など）に置き換わる
- **`unrestored_tjobs` への拡張**：ピッキング済みの TJob がコンベヤを埋めて次のピッキング作業をブロックする状況を表現できるようにする．入庫経路上のエッジの向きの意味はその際に定める
- **ピッキング済みバケットが作業場に残っている間の作業場ノード**：出口コンベヤの詰まりで搬出待ちの間は，当面アイドル作業場のダミーとして扱う
