# 搬送ジョブグラフ（TJob グラフ）の仕様

システム内の搬送ジョブ（`TJob`）をノードとし，ピッキング作業を行える順序をエッジで表す有向グラフの仕様．シミュレーション途中の状態の好ましさを評価し，ディスパッチングの意思決定（コントローラ）に用いることを目的とする．

> **ステータス**: ① 構築まで実装済み（`gtp/graph.py`）．② 評価（最長経路長の計算と閉路の除去）は未実装．対象範囲は `gtps.unpicked_tjobs`（最終的には `gtps.unrestored_tjobs` まで拡張する予定）．

TJob の状態遷移とバケットの所在については [tjob_lifecycle.md](tjob_lifecycle.md) を参照．

---

## 設計方針

- **`models.py` とは切り離す**：グラフ関連は `gtp/graph.py` に実装し，`models.py` の状態を読み取るだけで書き換えない．`models.py` から `graph.py` は参照しない
- **コントローラから利用する**：`DefaultController` を継承したカスタムコントローラが `TJobGraph` を保持し，ディスパッチのたびに `update()` で最新のグラフを得る
- **構築と評価を分ける**
  - ① 構築（`TJobGraph.update()`）：物理的な状態と先行関係をそのまま表す．閉路を含んでよい．エッジには長さそのものではなく，長さの内訳を持たせる
  - ② 評価：パラメータ（α，β）から長さを計算し，閉路を除去する操作をはさんで最長経路長などを求める
- **段階的に実装する**：`update()` はまず毎回スクラッチから構築する素直な実装とし，実行時間を計測してから差分更新（ノード集合と先行関係エッジのみ保持し，経路順序エッジは張り直す）を検討する

```python
class MyController(DefaultController):
    def __init__(self, env, gtps):
        super().__init__(env, gtps)
        self.tjob_graph = TJobGraph(gtps)

    def dispatch_shuttle(self, shuttle, candidate_tjobs):
        g = self.tjob_graph.update()  # 現時点の状態を反映したグラフ
        ...
```

## エッジの向き

すべてのエッジは **「先にピッキング作業を行える TJob → 後に回される TJob」** の向きに張る．

- 経路順序：作業場に近い（下流の）TJob → 遠い（上流の）TJob
- 先行関係：先の PJob の TJob → 後の PJob の TJob

両者が食い違う箇所（例：後の PJob の TJob が，先の PJob の TJob より経路上で前にいる）は閉路として現れる．構築時には閉路をそのまま残す．

---

## ノード

| ノード | キー | 説明 |
|---|---|---|
| スタート | `('start',)` | ダミー．1つだけ |
| アイドル作業場 | `('station', p)` | 作業場 p が作業中でないときのダミー |
| TJob | `('tjob', pjob.idx, tjob.idx)` | 対象範囲（`unpicked_tjobs`）の TJob |

作業場 p が作業中の場合は，作業中の TJob のノードが作業場ノードを兼ねる（アイドル作業場のダミーは作らない）．

### TJob の位置

各 TJob の位置は，**物理的な所在**（`tjob.bucket.cell`）で決める．割付け済みでもバケットを積む前（空車で迎えに行っている途中など）は，バケットの所在で判断する．設備（コンベヤ・リフト・シャトル・台車）は，TJob を積んでいるときだけその TJob のノードとして現れ，空の設備に対応するノードは作らない．

| 位置 | 該当する TJob |
|---|---|
| `station` | 作業場 p にバケットがあり，ピッキング作業中 |
| `conv2` | 作業場 p の入口コンベヤ（stage 2，出庫）上 |
| `car` | ループ台車に積まれた出庫ジョブ（`ON_FW_LOOP`） |
| `conv1` | 系列 a のループ入口コンベヤ（stage 1，出庫）上 |
| `lift` | 系列 a の出庫リフトに積まれている |
| `conv0` | 系列 a・階層 f のリフト入口コンベヤ（stage 0，出庫）上 |
| `shuttle` | 系列 a・階層 f のシャトルに積まれた出庫ジョブ |
| `store` | `TO_FW_SHTL` で，バケットが置場にある |
| `beyond_store` | 再搬送のため入庫経路を戻っている（`retry_needed == True`） |
| `off_route` | バケットの順番待ち（`bucket.current_tjob()` が自身でない） |

`station` から `store` までは，バケットの現在のジョブ（`bucket.current_tjob()`）である TJob に限る．再搬送中の TJob を積んだシャトル・台車は，出庫経路の上では空として扱う．

## エッジ

### 種類

| `kind` | 張り方 |
|---|---|
| `start` | S → 各作業場ノード |
| `chain` | 経路上で隣り合う TJob 間（空の設備は飛ばす） |
| `direct` | 台車（またはその代替）→ ループより上流にある同じ作業場行きの全 TJob |
| `precedence` | 同じ作業場の，隣り合う PJob の TJob 間 |
| `bucket` | 同じバケットで，割付け順に隣り合う TJob 間 |

### `chain`：作業場側

作業場 p ごとに，下流から上流へ次の順に結ぶ．

```
作業場 p → conv2 の TJob（下流から順に直列）→ 作業場 p 行きの TJob を積んだ台車（並列）
```

### `chain`：上流側

系列 a ごとに，下流から上流へ次の順に結ぶ．合流点では並列に分岐する．

```
conv1 の TJob（下流から順に直列）→ 出庫リフト → 各階層 f の conv0 の TJob（並列に分岐，各々下流から順に直列）
  → シャトル → 置場待ちの TJob（並列）
             → 置場の向こう側の TJob（並列）
```

置場の向こう側の TJob は，置場待ちの TJob と同じ起点から張る（置場待ちの TJob から張るのではない）．

### 空の設備の飛ばし方

途中の設備が空の場合は，それを飛ばして次に TJob がある位置に直接エッジを張る．たとえば出庫リフトが空なら conv1 の最上流の TJob から各階層の conv0 の最下流の TJob へ，conv0 も空ならシャトルへ，と順にたどる．

### `direct`：台車から上流へ

作業場 p ごとに，作業場 p 行きの TJob を積んだ全台車から，ループより上流（`conv1`・`lift`・`conv0`・`shuttle`・`store`・`beyond_store`）にある作業場 p 行きの**すべての** TJob にエッジを張る（全系列が対象）．作業場 p 行きの TJob を積んだ台車がない場合は，conv2 の最上流の TJob（conv2 も空なら作業場ノード）から張る．

同じ系列上で `chain` でたどれる TJob への `direct` は冗長だが，最長経路長には影響しないので絞り込まない．

### `precedence`

同じ作業場に割り付けられた PJob を `pjob.idx` の順に並べ，隣り合う PJob の TJob 間に，すべての組み合わせでエッジを張る．対象範囲の TJob を1つも持たない PJob は飛ばす．同じ PJob 内の TJob 間にはエッジを張らない．

### `bucket`

同じバケットに割り付けられた未完了の TJob（`bucket.undone_tjobs()`）を割付け順に並べ，隣り合う TJob 間にエッジを張る．

## エッジの長さ

### 境界の長さ

`chain`・`direct` の長さは，始点の位置から終点の位置まで上流へたどる間に越える境界の長さの合計とする．

| 越える境界 | 長さ |
|---|---|
| コンベヤ上で隣り合う TJob 間（作業場 → conv2 の最下流の TJob を含む） | 1 |
| 下流 → 台車（台車の出口側） | 1 |
| 台車 → 上流（台車の入口側） | α（設備の種類ごと：`loop`・`lift`・`shuttle`） |
| 置場 → 置場の向こう側 | β |

- 空の設備を飛ばしても，境界の合計は設備がある場合と一致する（例：空のリフトを飛ばす conv1 → conv0 のエッジは 1 + α_lift）
- 空のコンベヤは境界の長さに何も加えない（例：conv0 が空のとき，リフト → シャトルのエッジは α_lift + 1）
- `direct` は設備の境界のみを数え，途中にいる TJob の分は加えない（例：台車 → シャトル上の TJob は α_loop + 1 + α_lift + 1）

### 種類ごとの長さ

| `kind` | 長さ |
|---|---|
| `start` | 0 |
| `chain`・`direct` | 境界の長さの合計 |
| `precedence` | 1 |
| `bucket` | β |

基準の時間単位（1）はピッキング作業時間のイメージ．α・β は調整用のパラメータで，初期値はすべて 1 とする．

### 長さの内訳の持たせ方

① 構築では長さを確定させず，各エッジに内訳を属性として持たせる．

| 属性 | 意味 |
|---|---|
| `kind` | エッジの種類 |
| `n_unit` | 長さ 1 の境界の個数 |
| `alphas` | 越えた台車の入口側の種類のリスト（例：`['loop', 'lift']`） |
| `n_beta` | β の個数 |

長さ ＝ `n_unit` ＋ Σ α[`alphas` の各要素] ＋ `n_beta` × β として ② で計算する．`precedence` は `n_unit = 1`，`bucket` は `n_beta = 1`，`start` はすべて 0 となる．

## グラフの型

`networkx.MultiDiGraph` を用いる．同じノード対の間に種類の異なるエッジ（例：`chain` と `precedence`）が重なりうるため．エッジのキーは種類（`kind`）とする（例：`graph.has_edge(u, v, key='chain')`）．

## 実装（`gtp/graph.py`）

| 名前 | 説明 |
|---|---|
| `TJobGraph(gtps, scope='unpicked')` | グラフ構築器．`scope` は現在 `'unpicked'` のみ |
| `TJobGraph.update()` | 現時点の状態からグラフを構築して返す（毎回スクラッチから構築） |
| `edge_length(data, alpha=None, beta=None)` | エッジ属性の内訳から長さを計算する．省略時は `DEFAULT_ALPHA`・`DEFAULT_BETA`（すべて 1） |
| `tjob_key(tjob)`・`START` | ノードのキー |

ノード属性は `node_type`（`'start'`・`'station'`・`'tjob'`）のほか，TJob ノードには `position`・`picker`（行先作業場）・`pjob`・`progress`（int）・`aisle`・`floor`（置場の系列・階層）・`retry_needed`・`tjob`（元の `TJob` への参照）を持たせる．アイドル作業場ノードは `picker` を持つ．

構築処理は設備側から走査して各 TJob の位置を分類し，各位置で `progress` が想定どおりであることを `assert` で確認する．`random` は呼ばないので，グラフを使ってもシミュレーション結果は変わらない（`tests/test_graph.py` で golden 値により確認）．

観察用に `examples/inspect_tjob_graph.py`（引数：構築する時刻）があり，位置別ノード数，種類別エッジ数，サイズ2以上の強連結成分を表示する．
描画用に `examples/show_tjob_graph.py` があり，ノードを位置ごとの段（縦），作業場・系列・階層ごとの列（横）に並べて PNG に保存する（既定の保存先は `data/tjob_graph_t<時刻>.png`）．ノードの色は行先作業場，赤枠は閉路（サイズ2以上の強連結成分）に含まれるノード，`*` は再搬送中を表す．`--kinds` で描くエッジの種類を絞れる（閉路の判定は描かないエッジも含むグラフ全体で行う）．

```bash
uv run examples/show_tjob_graph.py --time 200                                    # 全種類のエッジを描画
uv run examples/show_tjob_graph.py --time 200 --kinds start,chain,precedence,bucket  # direct を除いて描画
```

**計測値（参考）**：`PJOB=100, SEED=1234` で，ディスパッチのたびに構築すると1回あたり約 0.3 ms，実行時間は約 0.4 秒から約 0.67 秒（約1.7倍）になった．

## 後回しにした項目

- **最長経路長の計算時の閉路の扱い**：② で「同じ作業場行きで PJob の順と逆向きの経路順序エッジを除外する」ような操作をはさむ．ただし，両端の TJob のみを見る除外では，別の作業場行きの TJob を介した閉路が残りうるため，除外後に DAG であることを確認する．具体的な規則は，実際のスナップショットで閉路の現れ方を確認してから決める
- **`unrestored_tjobs` への拡張**：ピッキング済みの TJob がコンベヤを埋めて次のピッキング作業をブロックする状況を表現できるようにする．入庫経路上のエッジの向きの意味はその際に定める
- **ピッキング済みバケットが作業場に残っている間の作業場ノード**：出口コンベヤの詰まりで搬出待ちの間は，当面アイドル作業場のダミーとして扱う
