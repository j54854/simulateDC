# 搬送ジョブグラフ（TJob グラフ）：文書の入口

シミュレーション途中の状態の好ましさを評価し，ディスパッチングの意思決定（コントローラ）に用いるためのグラフについて，系統ごとの文書の地図と，系統の間の関係をまとめる．各系統の定義・結果・未決事項は，それぞれの文書にある．

> **ステータス**（2026-11-28）: 現在の検討の中心は整流グラフ（[flow_graph.md](flow_graph.md)）．ブロックグラフ（[block_graph.md](block_graph.md)）は評価の段階 E1 まで実装済みで，比較・参照用として残す．2026-11-28 に，もとの tjob_graph.md（旧実装の仕様とブロックグラフの仕様が混在していた）を系統ごとのファイルに分け，この文書を入口として書き直した．

## 系譜

1. **旧実装（1ノード縮約）**：TJob をノード，`station`・`aisle`・`precedence`・`bucket` をエッジとし，エッジに長さの内訳を持たせた．最長経路で評価するつもりだったが，閉路が生じた（どの閉路も「到着順が減る向きの `aisle` ＋ `precedence`」を含む）．閉路を取り除く規則を探す中で，グラフの定義をオペレーショングラフから導き直すことにした
2. **オペレーショングラフ**：作業レベルで，機械の占有と no-buffer の制約を厳密に表す土台．オンライングラフ（時刻 t の状態から作る）は閉路を持たず，実現値ではスケジュールの下界になる
3. **ブロックグラフ**：オンライングラフを3ブロックに縮約した．到着と作業を分けたことで閉路は構造的に消えた．剛体近似で長さを定め，conv2 をバッファとして働かせるために作業ブロックにポートを入れた．参照実装・直接構築・評価 E1（作業場の直列化）まで実装し，時刻の誤差と，スロットごとの累積の遊びとの相関を測った．余裕のある条件では相関 0.6〜0.8 だったが，混雑した条件では低かった
4. **整流グラフ**：時刻の精緻化（E2・E3）を進めるより，順序の見方に切り替えることにした．作業場の効率が落ちるのは整流化の失敗（と復路の conv2 のブロッキング）による，という作業仮説に立ち，時刻の代わりに「どのディスパッチの判断点まで越えたか」を持たせる．旧実装の閉路は，整流化の失敗を示す信号として読み直す

**縮約と射影**：ブロックグラフも整流グラフも，オペレーショングラフ（のオンライングラフ）から導けるものとして定義し，実装では状態から直接作る．導出の手続きは名前で区別する．ブロックグラフの**縮約**は，作業をブロックにまとめて長さを剛体近似で導く（商グラフに近く，時刻を保つ近似）．整流グラフの**射影**は，作業のうち 12・18・22 だけを残し，エッジの種類ごとにその間の順序関係だけを写して推移的に簡約し，長さを捨てる（順序だけを残す．名前は手続きに付けたもので，既存のグラフ理論の用語ではない）

## 共通の用語

系統をまたいで使う用語と，定義の所在．

| 用語 | 意味 | 定義 |
|---|---|---|
| 作業番号（1〜34） | オペレーショングラフの作業 | operation_graph.md の「作業（ノード）」 |
| 鎖・扇・訪問 | 機械の上の確定した処理順・未確定の処理順・機械が TJob を1回扱う単位 | operation_graph.md の「機械の占有」「オンライングラフ」 |
| `aisle` | 同じ系列の FIFO の順（ループより上流） | tjob_graph_v1.md の「エッジ」．ブロックグラフでの扱いは block_graph.md の「エッジの種類」 |
| `station` | 同じ作業場行きの TJob の間の順（conv2・作業場） | 同上 |
| `precedence` | 作業場での処理順（PJob の順） | 同上 |
| `bucket` | 同じバケットを使う TJob の間の順 | 同上 |
| TJob の位置 | 状態ごとの TJob の分類 | tjob_graph_v1.md の「TJob の位置」，block_graph.md の「時刻 t での分割」 |

## 系統をまたぐ知見

- **旧実装の閉路 ＝ 整流化の失敗**：閉路は同じ系列の FIFO の中の逆転（作業場の順で後の TJob が前にいる）である．ブロックグラフでは到着と作業を分けて消したが，整流グラフではそのまま信号として使う（flow_graph.md の「旧実装・ブロックグラフとの関係」）
- **ポートの由来は B**：ブロックグラフの作業ブロックのポートは，conv2^BW の台車待ちが剛体近似で作業場を塞いだように見えることを防ぐために入れた．整流グラフでは，同じ制約をブロッキングエッジ 22_{k−C₂−1} → 18_k として表す
- **遊びの原因**：E1 の位置ごとの評価で，余裕のある条件の遊びの約半分は未投入の TJob を待つもの，混雑した条件では conv1・リフトが約半分，周回・再搬送が約1/4だった（block_graph.md の「E1 の位置ごとの評価」）．整流グラフの対象とする条件の選び方は，これを踏まえている

## 今後の方針

- 整流グラフが旧実装の進化版と位置づけられたら，その時点で旧実装の文書（tjob_graph_v1.md）を flow_graph.md に吸収しうる
- ブロックグラフ（ポートあり）は，整流グラフが成功しても比較・参照用として残す
